# 로컬 플레이어 모델 도입 검토용 현황

작성: 2026-10-21 11:15 KST 기준. 독자: 프로젝트에 합류하는 Claude 및 개발·조사 에이전트.

이 문서는 사용자 대화, 로컬 조회 결과, 프로젝트 소스와 기존 조사 기록을 정리한 정보 전달 자료다. 모델 선정이나 구현 방식을 확정하지 않는다. 로컬 모델 실험·설치·게임 조작은 이 문서 작성 과정에서 수행하지 않았다. 이 문서 자체가 게임 재시작·패치 배포·세이브 변경의 승인은 아니다.

## 1. 프로젝트 목적과 사용자 요구

- 대상 게임은 Lobotomy Corporation이다. 목표는 클리어 자동화뿐 아니라 AI가 관찰·선택·실수·수정·숙련을 거치며 경험을 남기고, 다른 모델이 그 기록을 출처와 함께 이어받도록 하는 것이다.
- 플레이어는 자신이 게임을 하고 있음을 안다. 시설 관리자는 게임 안의 역할이다.
- 경험에는 효율과 교훈 외에도 관심, 취향, 직원에 대한 평가, 스토리 감상, 행동 변화로 이어지지 않는 인상이 포함된다. 감정이나 실패를 의도적으로 만들어낼 필요는 없다.
- 게임기는 관찰·입력·기록 장치이고 판단은 플레이어가 맡는다. 게임기가 숨은 정답이나 공략을 제공하지 않는다.
- 플레이어가 활용할 게임 지식은 제공받은 화면·표시 정보·소리, 자신의 행동 결과, 출처가 있는 경험 기록을 기준으로 한다. 사전학습 지식의 실제 제거를 보장하는 시스템은 아니다.
- 사용자는 시각 정보를 전부 제거하려는 것이 아니다. 반복 운영에서 불필요한 이미지 인식과 호출을 줄이되, 스토리·새 연출·외형·시각적 단서는 직접 관람할 수 있어야 한다.
- 로컬 모델 검토의 계기는 현재 플레이 비용 부담이다. 사용자는 실시간 반응과 장기간의 기억 연속성도 중요하게 보고 있다.

- `run_player_mcp.py`는 플레이어 전용 stdio MCP 진입점이다. 합성 테스트용 도구와 실제 플레이 도구를 구분해야 한다.
- 실제 입력은 게임 내부 가상 포인터·키 입력을 이용한다. Codex Windows 브리지나 사람의 OS 마우스를 필수로 사용하지 않는다.
- 게임의 관찰 생산은 계속 진행되지만 모델이 인지하는 시점은 도구 결과를 받은 때다. 연속 생산이 모델의 연속 추론을 의미하지 않는다.
- 빠른 관찰은 구조화된 상태와 변경분을 제공한다. 이미지 확인도 별도로 가능하다. 모든 UI와 모든 보스 연출이 완전하게 구조화되었다고 보장하지 않는다.
- `perception.py`는 `priority_changes`와 일반 `changes`를 구분한다. 삭제·화면 이탈과 사망·파괴를 동일하게 해석해서는 안 된다.
- 간단 입력, 직원 이동, 짧은 입력 예약, 의도 묶음, 입력 후 관찰 반환 경로가 있다. 전송 성공은 목표 행동·도착·작업 완료의 증명이 아니다.
- 입력 대상은 화면/카메라 조건과 현재 유효성에 제한된다. 기존에 관찰한 고정 시설 지도와 현재의 동적 상태를 구분한다.
- 조건부 자동 일시정지는 플레이어가 활성화한 일회용 예약이다. 폭주 주기, 직원 사망, 환상체 탈출 조건이 있으며 사용 후 해제된다. 게임 자체의 일시정지 제한을 우회하는 기능은 아니다.
- 게임 생명주기는 Codex 앱과 분리되어 있다. 시작·종료는 검증된 런처/전원 경로를 사용한다.

## 5. 경험과 컨텍스트의 현재 경계

### 저장하는 정보

- 실제로 플레이어에게 반환한 관찰과 입력 결과.
- 플레이어가 채팅에 공개한 판단·감상·오해·정정의 원문과 시간순 기록.
- 일차/시도별 회고, 누적 기억, 출처가 있는 환상체·시련·상황별 플레이북.
- 취향과 스토리 감상도 경험으로 다룬다. 비공개 내부 추론 원문을 수집하는 시스템은 아니다.
- `Run`은 게임의 실제 1일차 회귀 횟수+1이다. 모델 교체나 새 채팅 자체가 새 Run은 아니다. 튜토리얼과 본편 일차는 구분한다.

관련 지침은 `config/player/AGENTS.md`, `vault/Lobotomy-Experience/Config/Player-Persona.md`, `Recording-Rules.md`, `Day-Review-Template.md`에 있다. 이전 모델이 남긴 경험과 새 모델 자신의 직접 경험은 구분한다.

### 호스트 이전 시 확인할 항목

`run_player_mcp.py`는 채팅 수집과 Git 동기화 서비스를 시작한다. 현재 `chat_capture.py`의 공개 채팅 수집 경로는 Codex rollout 기록을 기반으로 한다. 다른 로컬 호스트의 발언이 자동으로 같은 방식으로 수집된다고 보장할 수 없다. MCP의 경험 저장 기능 재사용과 호스트 공개 발언의 자동 수집은 별개로 검토해야 한다.

### 컨텍스트 관련 사실과 미확인점

- 사용자는 Codex의 컨텍스트 압축 도중 플레이가 멈추거나 대응하지 못하는 상황을 문제로 제기했다.
- 한 판단에 페르소나·사용 규칙·도구 정의·현재 상태·직전 행동·진행 중 명령·과거 경험이 함께 필요할 수 있다.
- 기록이 디스크에 존재하는 것과 필요한 시점에 모델 문맥에 포함되는 것은 다르다.
- 실제 메모리에는 가중치 외에도 문맥 캐시와 이미지 처리 등 실행 비용이 발생한다. 최대 문맥 메타데이터만으로 이 PC의 운용 문맥을 정할 수 없다.
- 앞선 대화에서 4천~8천 토큰이 짧은 연결 실험용 예시로 언급되었으나, 하루 전체 플레이에 충분하다는 측정 결과나 채택된 설정은 아니다.
- 현재 Codex 플레이어의 실제 문맥 길이·압축 임계치, 각 로컬 모델의 적정 문맥 길이, 기억 검색 누락률은 측정하지 않았다.
- 상태표 유지, 미완료 사건 목록, 선택적 기억 조회, 회고 분리 등은 대화에서 논의된 검토 항목이다. 로컬 플레이어용으로 구현·검증된 완성 구조는 아니다.

## 6. 지연과 정보량에 관한 기존 증거

아래는 [2026-10-20 조사](diff-optimization-audit-20261020.md)의 과거 기록이며 이후 패치가 반영되었다. 현재 응답량이나 개선 후 속도로 일반화할 수 없다.

| 당시 조사 항목 | 기록 |
|---|---|
| 관찰 18건 중 delta 9건 | JSON 문자 수 중앙값 27,925자 |
| 입력 결과 439건 | JSON 문자 수 중앙값 11,652자 |
| 특정 입력 영수증 20건 | 중앙값 313ms, 범위 188~610ms |
| 일부 입력 간 간격 | 약 30~40초 사례 |

문자 수는 토큰 수나 과금액이 아니다. 입력 사이 간격에는 모델·호스트·전송·사용자 대기가 섞일 수 있어 모델 추론 시간으로 단정할 수 없다. 관찰량 감소율을 플레이 속도 개선율로 환산할 근거도 없다.

사용자는 적 위치 변화의 늦은 인지, 폭주 대응 지연, 시련 종료 전 작업 재개 등의 사례를 보고했다. 특히 최근 호박빛 여명 관련 질문에 대해 화면 이탈/종료 혼동, 기존 계획 유지, 의도적 병행 등이 가설로 언급되었으나 해당 사례의 원인은 아직 로그로 확정하지 않았다. 이를 로컬 모델 도입의 해결 효과나 기존 게임기 결함으로 단정하지 않는다.

## 7. Codex·MCP·서브에이전트의 구분

- 모델, 모델을 실행하는 호스트, MCP 도구 서버는 서로 다른 구성 요소다. 이 프로젝트의 MCP 서버 자체가 플레이어 모델을 포함하는 것은 아니다.
- Codex의 서브에이전트는 별도 작업을 위임받는 에이전트 실행 단위다. 플러그인/MCP 호출이 곧 서브에이전트 실행이라는 뜻은 아니다.
- 공식 문서는 서브에이전트가 별도 모델·도구 작업을 수행하므로 단일 에이전트보다 토큰 사용량이 늘 수 있다고 설명한다.
- 실제 기존 플레이어 세션에서 서브에이전트가 얼마나 사용되었는지는 이번에 조사하지 않았다. Astra Light를 쓴다는 사실만으로 다중 에이전트 플레이를 가정하지 않는다.
- 로컬에서 한 모델을 여러 대화에 공유하는 구성과 여러 모델을 동시 로드하는 구성은 자원 사용이 다르다. 이 PC에서 어느 쪽도 플레이 실험을 하지 않았다.

공식 참고: [Codex 서브에이전트](https://learn.chatgpt.com/docs/agent-configuration/subagents).

## 8. 검토 시 아직 답이 필요한 질문

1. 현행 빠른 관찰과 도구 정의를 넣었을 때 실제 입력 문맥이 얼마나 되는가? 긴 플레이에서 어떻게 증가하는가?
2. 각 설치 모델의 짧은/긴 문맥별 로딩 메모리, 첫 응답 지연, 완전한 도구 호출까지의 시간은 얼마인가?
3. 도구 사용·직원 식별·복수 작업 관리·이미지 관람·한국어 회고의 성공률은 어떠한가?
4. 현재 상태, 과거 관찰, 미확인 추정, 미완료 명령을 구별하면서 기억을 이어갈 수 있는가?
5. 게임·녹화와 동시 실행할 때 CPU/GPU/RAM 경쟁과 프레임 저하가 발생하는가?
6. 단일 로컬 플레이어, 역할별 문맥 분리, 복수 모델, 클라우드 혼합 구성 각각의 비용·지연·경험 귀속은 어떻게 다른가?
7. 현행 MCP를 연결할 호스트가 이미지 반환, 반복 도구 사용, 사용자 개입, 예약 취소, 기록 저장을 지원하는가?
8. Codex 전용 공개 채팅 수집·압축 연동 등을 어느 범위까지 재사용하거나 대체해야 하는가?
9. 기존 구독만 이용하는 경우와 별도 API를 사용하는 경우를 구분했을 때 허용 비용 내 운영 가능한가?

이 문서는 특정 답이나 모델을 권고하지 않는다. Qwen3.5-4B도 앞선 대화에 후보로 언급되었으나 현재 설치 목록에는 없고 비교 실험도 하지 않았다.
