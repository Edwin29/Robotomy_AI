# 초 단위 플레이와 모델 비용 문제에 대한 조언 — 2026-10-20

작성: Claude (조언 역할). 코드·설정은 바꾸지 않았다. 근거는 현재 저장소 문서
([최적화 조사](diff-optimization-audit-20261020.md), [로컬 모델 계획](local-decision-model-experiment.md))와
Run-001 기록(9일차 Attempt 01~12)이다. 모델별 가격은 확인하지 않았으므로 수치 대신 계산식으로 적는다.

## 결론 먼저

**LLM을 초 단위 조종사로 쓰는 구조를 바꾸는 것이 핵심이다.** 지금은 “관찰 → LLM 추론 → 클릭 1회 → 결과 관찰”이
한 바퀴에 30~40초 걸린다. 모델을 바꾸거나 JSON을 줄이면 이 시간을 몇 배 줄일 수는 있다. 하지만 사람의 0.3초 반사에는
닿지 않는다. 대신 시간 척도를 세 층으로 나눈다.

| 층 | 시간 척도 | 담당 | 예 |
|---|---|---|---|
| 반사 | 0.1초 | 게임기 안의 코드. 플레이어가 미리 정한 조건만 실행한다 | 경고음·사망 로그·HP 급감이 보이면 일시정지, 작업 완료를 기다렸다가 깨우기 |
| 실행 | 1~5초 | 작고 빠른 모델(Luna) 또는 결정적 매크로 | 정해 둔 배정 순서 수행, 집결 명령, 상태 확인 |
| 계획 | 수십 초~분, 사건 때만 | 큰 모델(Astra/Sol) | 하루 계획, 시련 대응 방침, 사망·패닉 후 재판단, 회고 |

이렇게 나누면 비싼 모델은 하루 수십 번만 부르고, 빠른 모델이 나머지를 맡는다. 남는 위험 순간은 반사 층의 일시정지가 받아 준다.

## 1. 지금 시간이 어디서 새는가

- 입력 영수증은 중앙값 313ms(188~610ms)인데 입력 사이 간격은 30~40초다([최적화 조사](diff-optimization-audit-20261020.md)).
  게임기는 이미 빠르고, 남는 시간은 거의 모델 쪽(추론 + 긴 입력 읽기)이다.
- 관찰 하나가 매우 크다. delta 중앙값 약 2.8만 자, full 약 6만 자이고, 그 안에 소리 9천 자와 시설 목록 6천 자가 있다.
  한국어 JSON 기준으로 대략 1~3만 토큰이다. 이 크기는 매 호출의 **첫 토큰 지연과 비용을 함께** 키운다.
- 9일차 실패 기록에도 같은 패턴이 보인다. “다음 HP 조회 때 Bat 사망”(Attempt 11), “집결 확인 전에 시련 발생, 빅토르 단독 전투 사망”(Attempt 07)처럼,
  위험이 생긴 순간이 아니라 **다음에 볼 때** 알았다. 마지막 시도는 사용량 부족으로 멈췄다(Attempt 12).

먼저 계측부터 권한다. 호출마다 모델 대기 시간, 도구 실행 시간, 입력·출력 토큰 수를 남기면, 아래 조치들이 실제로 얼마나 효과가 있는지 바로 비교할 수 있다.

## 2. 해결책 (효과 큰 순)

### ① 기다리는 도구: `wait_for_event` (지연·비용 모두 큼)

지금 MCP는 모델이 물어볼 때만 답한다. 모델이 “다음에 볼 때”까지 사건을 모르는 이유다. 반대로 하면 된다. 모델이 조건을 주고 도구를 부르면,
게임기가 조건이 맞거나 시간이 다 될 때까지 응답을 잡고 있다가 그때 돌려준다. 예를 들어 이렇게 부른다.

```
wait_for_event(timeout_s=20, on=["새 경고음", "새 알림/사망 로그", "직원 HP가 보이는 값 기준 30% 이하", "작업 완료"], pause_on_trigger=true)
```

- 기다리는 동안 모델은 토큰을 쓰지 않는다. 같은 20초를 1초마다 관찰로 채우는 것보다 훨씬 싸다.
- 조건은 **플레이어가 고른다.** 게임기는 표시된 정보가 조건과 맞는지만 기계적으로 확인한다. 위험을 대신 판단하지 않는다.
- 돌려줄 때는 그동안 일어난 일을 시간순 목록으로 함께 준다(이전 문서의 A1 제안).

**결정 필요:** `pause_on_trigger`는 현재 원칙(게임기 자동 일시정지 금지, 블록 자동화 보류)과 겹친다. 플레이어가 미리 정한 조건일 때만 일시정지하는 것을
“사람의 반사 신경 대체”로 허용할지는 사용자가 정해야 한다. 허용하지 않아도 이 도구는 깨우는 역할만으로 효과가 크다.

### ② 관찰 다이어트: 호출당 1~2천 토큰 목표 (지연·비용 큼)

Codex가 [최적화 조사](diff-optimization-audit-20261020.md)에서 이미 방향을 잡았다(시설 diff 5,886→387자 등). 거기에 두 가지를 더한다.

- **고정 앞부분 + 짧은 뒷부분.** 규칙, 지도, 플레이북처럼 하루 동안 변하지 않는 내용은 매 호출 같은 순서로 맨 앞에 두고, 바뀐 것만 뒤에 붙인다.
  API를 쓴다면 프롬프트 캐시로 앞부분 비용과 지연이 크게 준다. 구독에서도 문맥이 짧아지면 사용량 한도에 덜 걸린다.
- **기본은 요약, 상세는 요청 시.** 기본 응답에는 경고, 내 직원 상태 한 줄씩, 바뀐 것만 담는다. 소리는 경고·새 소리만 남기고 반복은 묶는다.
  나머지는 `detail(room=…)`처럼 물을 때만 준다.

### ③ 클릭 대신 의도 단위 행동 (호출 수 큼)

이미 `game_input`, 시설ID→작업→직원 행 배정, `move_employee`가 있어서 방향은 맞다. 더 밀면 이렇다.

- “에덴: 애착 → O-09-91”, “정보팀 전원 → 우하단 복도”처럼 **한 호출에 여러 의도**를 받는다. 실행할 때마다 현재 화면에서 대상을 다시 확인한다.
- 결과는 성공 여부를 단정하지 않고, 의도별로 화면에서 확인된 것과 안 된 것만 돌려준다.
- 9일차의 “준비 드래그 중 애니메이션 좌표 오입력”처럼 반복되는 실수는 의도 단위 행동으로 사라진다.

### ④ 모델 역할 분담 (비용 큼)

| 역할 | 추천 | 부르는 때 |
|---|---|---|
| 계획·위기 판단 | Astra 또는 Sol, 추론 중간 | 하루 시작, 시련 예고·발생, 사망·패닉, 하루 종료 회고. 하루 수십 회 |
| 실행 | Luna light | 계획 안의 단계 수행, `wait_for_event` 반환 처리 |
| 반사 | 코드(①) | 상시 |

Luna가 성급한 이유는 단독으로 전략까지 정하기 때문으로 보인다. Luna에게는 **큰 모델이 써 준 짧은 계획과 체크리스트**만 주고,
계획 밖 상황(새 환상체, 시련, 사망)이 오면 스스로 판단하지 말고 일시정지 후 큰 모델을 부르게 한다. “계획에 없으면 멈추고 올린다”가 핵심 규칙이다.

### ⑤ 비전은 필요한 곳만, 잘라서

- 전체 화면 대신 **필요한 영역만 잘라** 보내면 이미지 토큰과 판독 오류가 함께 준다. 게임기가 “구조화하지 못한 보이는 영역” 좌표를 주면 그 부분만 잘라 본다.
- 스토리·새 환상체 외형·보스 연출처럼 이미지가 본질인 장면은 계획 층(큰 모델)이 보고, 실행 층은 텍스트만 쓴다.
- 반복되는 이미지 판정(아이콘 상태 등)은 텍스처를 텍스트로 바꾸는 지금 방식을 계속 넓히는 것이 가장 싸다.

## 3. 사람과의 공정성

로보토미 코퍼레이션은 일시정지를 전제로 설계된 게임이고, 사람도 위기마다 일시정지한다. 따라서 “멈추고 생각하기”는 사람과 같은 수준의 플레이로 볼 수 있다.
다만 게임이 정지를 막는 구간은 우회하지 않는다. 반사 층(①)의 자동 일시정지를 쓰면 “사람보다 반사 신경이 빠르다”는 이점이 생긴다.
이것을 실험 조건으로 기록하고, 정지까지 사람 수준의 지연(예: 0.3~0.5초)을 일부러 넣을지도 정해 두면 좋다.

## 4. 비용 계산 방법

```
하루 비용 ≈ Σ(호출 수 × (입력 토큰 × 입력 단가 + 출력 토큰 × 출력 단가))  ← 캐시된 입력은 캐시 단가
```

- 지금 구조: 하루 호출 수백~천 회 × 1~3만 토큰 → 입력만 하루 수백만~수천만 토큰. 비싼 모델이면 부담이 클 수밖에 없다.
- 위 구조: 계획 모델 30~50회 × 1만 토큰 + 실행 모델 300~600회 × 2천 토큰 → 입력이 대략 한 자릿수 백만 토큰 이하로 준다(추정).
- 구독(Codex Pro)은 계획 층과 개발에 계속 쓰고, 실행 층만 API의 저가 모델이나 로컬 모델로 옮기는 혼합안이 현실적이다.
  RTX 4060 8GB면 3~8B 양자화 모델로 분류·반사 판단 정도는 가능하다. 전략 판단까지 맡기기는 어렵다.
- 결정 전에 하루치 실제 토큰 수를 계측해 위 식에 넣어 보길 권한다. 단가는 이 문서에서 가정하지 않았다.

## 5. 추천 순서

1. 계측: 호출별 모델 시간·도구 시간·토큰 기록 (반나절, 위험 없음)
2. 관찰 다이어트 ②와 `wait_for_event`의 깨우기 기능 ① (가장 큰 효과)
3. 의도 단위 행동 확장 ③
4. 계획/실행 모델 분리 ④. 같은 저장 상태에서 9일차를 반복해 Luna 단독, Astra 단독, 분리 구조를 비교한다(생존 수, 에너지, 비용, 사용량)
5. `pause_on_trigger` 허용 여부를 사용자가 결정한 뒤 반사 층 완성

①의 일시정지 부분만 기존 원칙 변경이 필요하고, 나머지는 현재 원칙 안에서 할 수 있다.
