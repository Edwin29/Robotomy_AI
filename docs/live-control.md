# 독립 로컬 입력 실행기와 판단 관찰

실제 입력은 `robotomy/virtual_input.py`와 복사본의 `VirtualInput.cs`가 담당한다.
Codex Windows 브리지, `@oai/sky`, node_repl, 브라우저 자동화는 필요하지 않다.
OS 포인터를 움직이지 않는 게임 내부 가상 입력이며 별도 모델/API 호출을 하지 않는다.
LLM은 보이는 화면을 해석하고 다음 행동을 고른다. 실행기는 그 행동의 가상 좌표와 입력 시간을 처리한다.
LLM 추론 시간·사용량은 여전히 필요하며, 실행기만 켜 놓으면 스스로 게임을 판단하는 구조는 아니다.

최신 결과: [최소 게임기 검증](console-minimum-verification.md).
`VirtualCursor.cs`는 게임의 Cursor 잠금/숨김/모양 요청도 가상 장치 안에서 처리한다.
원래 DeployUI.Start의 Confined 설정 때문에 사람 마우스가 갇힐 수 있던 경로를 차단했다.
게임 창을 활성화해도 Windows 커서 범위가 전체 화면으로 유지되는지 별도 측정했다.
실제 플레이 시험에는 OS 포커스·마우스 조작을 사용하지 않았다.
`scripts/player_trial.py`는 자동 정책 없이 한 행동과 후속 관찰을 기록하는 보조 CLI다.

## 연결과 실행

게임은 기존과 같이 `Launch-Live.cmd` 또는 `scripts/launch_live.py`로 실행한다.
게임 관찰 모드 → UI JSON/PNG → LiveReader → LLM 판단 → 로컬 가상 입력 → 후속 관찰 순서다.
복사본의 managed Input 호출을 가상 상태 읽기로 치환한다. 게임의 일반 UI 이벤트 처리는 그대로 사용하며 작업 완료·체력·게임 규칙을 직접 조작하지 않는다.

MCP 도구는 총 19개다. 실제 조작 순서:

1. `capture_live_control`: 최신 view_id, UI 표본, frame_path를 받는다. 입력은 없다.
2. 필요하면 `view_live_frame`으로 픽셀을 확인한다. 가려진 UI 텍스트는 판단 근거로 쓰지 않는다.
3. `prepare_live_action`: view_id, 행동, 이유, 예상 결과를 먼저 기록한다.
4. `execute_live_action`: 독립 실행기로 한 행동을 수행하고 receipt를 반환한다.
5. 새 `observe_live`를 읽고 `record_live_outcome`에 실제 관찰 결과를 연결한다.

`execute_live_action` 뒤에 별도 브리지 소비 호출은 필요하지 않다.
`live_action_receipt`와 `read_live_timeline`으로 상태와 기록을 다시 읽을 수 있다.
MCP를 쓸 수 있는 다른 로컬 클라이언트도 같은 서버를 사용한다. 이 채팅에 새 도구가 자동 로딩되었다는 뜻은 아니다.

CLI도 같은 실행기를 사용한다. 아래 명령은 저장소 루트/프로젝트 venv 기준이다.

```powershell
.\.venv\Scripts\python.exe -m robotomy live-capture
.\.venv\Scripts\python.exe -m robotomy live-resume
# live-capture에서 얻은 view_id와 실제로 관찰한 좌표를 사용한다.
'{"view_id":"FRESH_VIEW_ID","kind":"key","key":"d","duration_ms":1500,"rationale":"이동 교육의 WASD 안내","expected":"화면 이동"}' | .\.venv\Scripts\python.exe -m robotomy live-action
.\.venv\Scripts\python.exe -m robotomy live-pause
```

`scripts/live_step.py`는 방금 화면을 확인한 로컬 호출자를 위한 편의 도구다.
view_id 없이 위 행동 JSON을 stdin으로 주면 캡처→판단 기록→한 행동→2초 후 관찰을 수행한다.
자동 플레이 루프나 화면 의미 판별은 포함하지 않는다. 같은 대기열을 외부에서 넣은 경우
`live-execute-pending`은 최대 한 요청만 소비한다. 장기 서비스/상주 키보드 훅은 없다.

## 클릭 없는 hover 확인

최신 `capture_live_control`의 view_id와 화면에서 고른 대상 중앙 x/y를
`hover_live_control(view_id, x, y, settle_ms=500)`에 준다. 가상 포인터만 한 번 옮긴 뒤
200..1500ms를 기다리고, 그 시점 이후에 찍힌 검증된 PNG를 같은 응답으로 제공한다.
포인터는 다음 입력까지 유지된다. `frame_returned`는 설명이 표시되었다는 자동 판정이 아니다.
플레이어가 이미지를 확인해야 하며, 가장자리에서 반응이 없으면 보이는 다른 중앙 지점을 시도한다.
이 도구는 대상 좌표를 자동 탐색하거나 클릭하지 않고, 숨겨진 설명·UI hitbox를 제공하지 않는다.
대기 중 입력 잠금을 유지하여 다른 입력 예약과 섞이지 않는다. Stop·장면/해상도 변경·프레임
기한 초과는 영수증을 보존한 상태로 중단하며 입력을 재전송하지 않는다.
새 MCP 도구이므로 기존 연결에서는 재연결 후 안내를 다시 읽어야 한다.

## 입력 계약

좌표는 **게임 PNG의 좌상단 기준 픽셀**이다. 시작 기본값은1280×720이며 창 테두리/제목줄은 포함하지 않는다.
게임 안 가상 좌표로 전달하며 OS 화면 좌표나 DPI 변환이 필요 없다. 청록색 십자와 AI 표기가 가상 포인터다.

### 관찰 창 크기 조절과 녹화

분리 실행본 Lobotomy_Observer는 일반 창 테두리 드래그를 지원한다. 드래그를 마치면
16:9 비율로 자동 정렬한다. 최대화 버튼은 해당 모니터 작업 영역 안에 들어가는 가장 큰
16:9 일반 창으로 맞춘다(최대1920×1080). 게임 메인 스레드의 PNG 처리 부하를 제한하기 위해
현재 검증한 Full HD를 상한으로 둔다. 실행기에서
검증한 해당 PID/실행 경로/창 제목에만 Windows 크기 조절 스타일을 적용한다. 원본 게임,
DLL, 저장 파일은 변경하지 않으며 사람 마우스 입력을 게임으로 전달하지 않는다.
이미 실행 중인 창에는 `scripts/observer_window.py --enable-resize`로 적용할 수 있다.
`--size 1600 900`처럼 렌더 영역의 물리 픽셀 크기를 지정할 수도 있다.
observer_window.py의 숨김 보조 프로세스가 창 크기/이동 상태만250ms 간격으로 확인하고,
게임 프로세스가 끝나면 종료된다. 한 게임 PID당 하나만 실행한다. 게임 입력/AI 추론을 수행하지 않는다.

Unity 캡처와 표시 좌표는 새 해상도를 따른다. 크기 변경 시 벡터는 재측정하며, 이전 크기의
입력은 거부한다. 입력 중 크기가 바뀌면 가상 키/버튼을 해제하고 unknown을 반환한다.
플레이어는 새 캡처 후 다시 판단한다. 캡처 도중 JSON과 PNG 크기가 달라지는 경우도 거부한다.
창 확대는 렌더링/PNG 작업량을 늘린다. 녹화는16:9 크기(1600×900 또는1920×1080)를 권장하며
크기 조절 중에는 잠시 관측이 갱신되지 않을 수 있다. 창 크기를 정한 뒤 플레이를 시작하면
크기 변경에 따른 입력 중단을 피할 수 있다. 웹 관찰 페이지의2초 갱신은 녹화 프레임률이 아니다.

| kind | 값 | 동작 |
|---|---|---|
| move | x, y | 클릭 없이 포인터 이동 |
| click / right_click | x, y, duration_ms | 좌/우 클릭, 기본 80ms |
| key | key, duration_ms | 키를 누르고 지정 시간 후 해제 |
| scroll | x, y, scroll_y | 해당 위치에서 휠; 양수=아래, 음수=위, 절댓값 1..600. 가상 실행기에서 120=한 칸, -240=위 두 칸 |
| drag / right_drag | x, y, to_x, to_y, duration_ms | 좌/우 버튼 유지 중 보간 이동 후 해제 |

duration_ms는 20..3000이다. 허용 키는 Space/Escape/Return/1/2/3/WASDFG이며
대소문자와 앞뒤 공백을 정규화한다. Esc/Enter/Spacebar도 같은 키로 처리한다.
조합키·동시 키 입력은 지원하지 않는다. action kind도 앞뒤 공백과 대소문자를 정규화한다.
key에는 좌표를, 클릭에는 드래그 끝점 등을 섞지 않는다. 해당 입력에 관계없는 인자는 준비 단계에서
거절한다. move는 위치 설정이며 scroll은 한 번의 휠 입력이다(유지 시간 동안 반복되지 않음).
긴 입력을 끝낼 유효시간과 250ms 여유가 없으면 새 관찰을 요구한다. 준비와 전송 직전에 확인하지만
게임 지연까지 보장하지 않으므로 영수증과 후속 관찰을 계속 확인한다.
각 호출은 한 행동이며 임의 텍스트나 OS 단축키를 실행하지 않는다.
뷰는 30초, 준비한 판단은 최대 25초 동안 유효하다. UI가 바뀌면 더 일찍 다시 관찰한다.

## 화면과 중지

실제 게임은 `Lobotomy_Observer` 창에서 실시간으로 볼 수 있다.
[관찰 페이지](http://127.0.0.1:8765/)는 게임 이미지와 선택 이유·예상·입력·결과를 약 2초마다 갱신한다.
서버 실행: `.venv\Scripts\python.exe scripts\live_monitor.py` (127.0.0.1만 수신).

관찰 페이지는 GET 전용이며 POST는 405로 거절한다. 페이지의 클릭/키 입력은 게임으로 전달하지 않는다.
게임 창에서도 일반 관리 UI와 키 입력은 가상 상태를 읽으므로 사람 마우스와 분리된다.
게임이 다른 창 뒤에 있어도 동작한다. 최소화하면 프레임 수집이 멈출 수 있으므로 최소화는 피한다.

`live-pause`로 입력을 중지한다. 게임 창에 포커스가 있는 경우 물리 F8도 비상 중지로 읽는다.
게임 쪽에서 프레임마다 중지·유효시간·장면·해상도를 검사하고 가상 키/버튼을 해제한다.
동작은 최대 3초이며, Python이 죽더라도 게임 쪽 유효시간으로 해제된다. 게임 자체가 정지하면 프레임 기반 처리도 정지한다.
OS 키는 누르지 않으므로 OS에 눌린 키가 남는 구조가 아니다.
중지는 게임 시간을 멈추거나 이미 수행한 행동을 되돌리지 않는다.
`live-resume`은 이전 판단을 무효화한다. 새 화면과 새 판단으로만 재개한다.

## 저장 보호와 기록

- 준비된 복사본의 절대 실행 경로, PID, 저장 identity, 씬, UI 신선도를 확인한다.
- 각 입력 전에 원본 29개 저장 파일, PlayerPrefs, 원본 PlayerSettings 무변경을 검사한다.
- 가상 모드가 없거나 오래된 상태이면 거부한다. OS 입력으로 자동 전환하지 않는다.
- 독점 요청 파일·영구 claim·게임 ack로 같은 행동을 중복 실행하지 않는다.
- 실패 후 unknown은 자동 재시도하지 않는다. 화면을 관찰하고 새 판단을 만든다.
- 비정상 종료로 request/claim만 남은 경우 자동 복구하지 않는다. 기록과 실제 화면을 확인한 뒤 운영자가 정리한다.
- `.robotomy/live/control/events/`는 원본 이벤트, `views/`는 좌표 메타데이터와 PNG다.
- `vault/Live/Current-control.md`는 최근 100개 이벤트를 보여 주는 Obsidian 보기다.
- 이유는 행동 전에 선언한 간단한 설명이며 내부 사고 과정의 증명이 아니다.
- `input_sent`는 입력 전달이다. 교육 성공은 별도의 실제 관찰로 검증한다.
- UI JSON과 PNG는 비동기로 수집된다. 같은 순간을 나타낸다고 가정하지 않는다.

UI JSON의 `read_only`는 관찰 데이터의 성격이다. 전체 시스템은 가상 입력도 수행하며 오버레이는 `VIRTUAL INPUT`으로 표시한다.
이는 저장 경로 분리이며 OS 보안 샌드박스가 아니다. 백업/복구는 [live-adapter.md](live-adapter.md) 참고.
실제 경험의 모델 이전 번들 통합은 아직 별도 작업이며 합성 경험에 섞지 않는다.

## 이전 구현과의 관계

이전 `scripts/live_bridge.mjs`는 역사적 sky 브리지 구현이며 현재 실행 경로에서 사용하지 않는다.
이전 카티아 첫 작업 기록에는 사용자 이동 보조가 있었다. 해당 기록은 보존한다.
2026-10-17 독립 실행기 재검증은 튜토리얼 1을 처음부터 다시 시작했으며, 결과는 인계 문서에 별도로 기재한다.

## 현재 인지 방식과 범위

Unity의 활성 UI Text/기본 Button을 JSON으로 약 1초 간격으로 내보내고, 렌더링된 PNG를 약 2초 간격으로 수집한다.
LLM은 텍스트·좌표와 필요할 때 이미지를 읽고 한 행동을 선택한다. 프레임마다 LLM이 판단하는 구조나 순수 픽셀 기반 플레이는 아니다.
가려진 UI, 장면 뒤의 텍스트, 이미지 전용 버튼, 비동기 JSON/PNG 때문에 오인할 수 있다. 클릭 후에는 후속 화면으로 결과를 검증한다.

현재 입력 치환은 Assembly-CSharp와 UnityEngine.UI의 92개 managed 메서드에 적용된다.
네이티브 OnMouse/IMGUI/IME 텍스트 입력까지 게임 전체의 모든 입력 경로가 완전 분리됐다고 보장하지 않는다.
이번 관리자 튜토리얼에서 쓰인 UI 클릭·드래그·우클릭·키 입력은 실제 게임으로 검증한다.
`native_input.py`와 `live_bridge.mjs`는 이전 구현 보존용이며 CLI/MCP 기본 경로에서 호출하지 않는다.

## 플레이어 전원 도구

`start_game`, `close_game`, `game_power_status`가 player MCP에 추가되었다.
고정된 사본만 공식 무결성 검사 런처로 실행한다. start는 비동기 starting 응답 후 다시 확인한다.
close는 실행 경로·격리 저장 경로·창 PID 확인 후 WM_CLOSE만 보내며 강제 종료하지 않는다.
종료 요청 성공과 실제 종료/저장 성공은 다르다. 미저장 진행은 사라질 수 있다.
입력 대기 중 종료를 거절하며 과거 입력 결정은 무효화한다. PAUSED는 해제하지 않는다.
전원 조작은 활성 경험 시도에 기록되지만 시도 종료/Run 증가는 자동 수행하지 않는다.
기존 MCP 프로세스는 새 도구 등록을 위해 재연결해야 한다.
