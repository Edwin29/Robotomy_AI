# 플레이어 개인 대처 매뉴얼

`vault/Lobotomy-Experience/Playbook`은 회고와 별도로 필요할 때 참조하는 실용 메모 공간이다.
환상체별 관리·제압, 시련, 여러 조건이 겹친 상황, 도구 활용 절차 등을 자유롭게 구성한다.
개발자는 게임 공략이나 실제 플레이어의 대처법을 미리 채우지 않는다.

## 작성과 찾기

`save_playbook_entry(entry={...})`로 새 메모를 만든다. 필수는 title, author뿐이다.
나머지는 임의 JSON 필드이며 플레이어가 구조를 바꿀 수 있다. 아래는 게임 공략이 아닌 형식 예시다.

```json
{
  "title": "내가 정한 제목",
  "author": "플레이어 이름",
  "category": "자유로운 분류",
  "subject": "관찰한 대상 이름",
  "tags": ["관리", "제압"],
  "summary": "검색 결과에서 볼 짧은 설명",
  "content": {
    "내가 확인한 조건": [],
    "다음에 해볼 것": [],
    "도구 사용 예시": {},
    "아직 확실하지 않은 점": []
  }
}
```

content도 필수 형식이 아니다. 문자열, 표를 표현한 배열, 별도 필드 등으로 대체할 수 있다.
예약 필드 category/subject/summary는 문자열, tags/evidence_ids는 문자열 배열,
startup은 불리언, status는 active/archived이다. 저장소가 id/revision/updated_at을 붙인다.
이 세 필드는 수정 entry에서 빼고 기존 ID·revision은 도구의 entry_id·expected_revision으로 보낸다.
수정은 전체 메모 교체 방식이며 이전 버전은 JSON의 revisions에 남는다.
개별 리비전은 64 KiB까지이며 큰 자료는 메모 여러 개로 나누고 ID로 연결할 수 있다.

`read_playbook(query="대상명 제압")`은 모든 단어가 포함된 최신 메모를 찾는다.
분류 필터·보관 처리 포함·페이지 조회를 지원한다. 짧은 목록에서 ID를 골라
`read_playbook(entry_id="pb_...")`로 본문을 읽는다. include_history=true는 이전 버전도 반환한다.
startup=true인 메모의 요약만 기존 read_player_memory에 함께 나오며 하루 시작 전용은 아니다.

## 기록과 실행

입력 장치와 연결된 실행 기능은 없다. 저장된 도구 예시·절차·코드는 데이터다.
플레이어가 현재 상황과 화면을 확인하고 기존 입력/예약 도구로 실행한다.
과거 좌표/target_id는 현재 조작 대상이 아니다. 게임기는 메모의 정답 여부를 판단하지 않는다.
실제 경험 event ID를 evidence_ids에 넣으면 존재 여부를 확인한다.
가설·시도 결과·확신 수준의 표현 방식은 플레이어가 정한다. 사전 지식 제한은 그대로다.
활성 플레이 시 저장/조회 응답은 경험 기록에도 연결되지만 매번 기록할 의무는 없다.

JSON이 원본, Markdown은 Obsidian용 보기다. 기존 Git 게시자는 이 폴더를 자동 동기화 대상으로
취급하며 경험 내보내기도 포함한다. 이 기능 자체는 Git push를 기다리지 않는다.
원자적 파일 교체, 저장 잠금, expected_revision 비교로 동시 수정 시 덮어쓰기를 막는다.

## 검증 및 적용

임시 저장소에서 자유 형식/분류, 구조 변경, 이력 보존, 충돌, 보관/시작 요약, 근거 ID,
경로 제한, 다른 저장소에서 읽기, 경험 내보내기를 검증했다. MCP stdio 왕복에서도
저장 → 검색 → 원문 읽기 → 시작 메모 전달을 확인했다. 실제 플레이 기록에는 테스트 메모를 만들지 않았다.
전체 회귀 197개 중 도구 수 변경에 따른 기대값 1개를 갱신했고 해당 테스트 모듈 4개 재검증 통과.
새 MCP 연결은 ready이며 플레이어 도구 33개(호스트 상태 도구 포함)를 제공한다.
게임 DLL이나 프로세스·세이브는 변경하지 않았다. 기존 MCP는 새 도구 등록을 위해 재연결해야 한다.
