# 장기 진행 방향: 여러 게임과 경험을 쌓는 Persona — Claude 의견 (2026-10-21)

작성: Claude (조언 역할). 코드·게임은 건드리지 않았다.
전제는 [결합 검토](claude-persona-integration-20261021.md) 9절의 사용자 결정이다. Persona가 MCP를 호출하고, 플레이어는 Persona이며, 판단 Persona는 하나다. 기억의 주인은 Persona이고, 실행 중 들어온 입력은 다음 단계 경계에서 받는다.
목표: 이 시스템을 유지보수하면서, 같은 Persona가 Lobotomy 다음에도 다른 게임과 경험을 계속 얻는다.

## 핵심 방향

**Persona는 하나로 키우고, 환경은 갈아 끼울 수 있게 만든다.** 둘 사이에는 작은 공통 계약 하나만 둔다.

```text
            ┌──────────── Persona (AI_Persona_Pre) ─────────────┐
            │ Foundation: 실행·기록·권한·스케줄러·복구           │
            │ Agent Plane: Cognition · Memory · Self · Relation  │
            │              Activity Context(환경별)              │
            └──────────────────────┬────────────────────────────┘
                                   │  Environment Contract (버전 관리)
              ┌────────────────────┼────────────────────┐
         Lobotomy (Lobotomy)   다음 게임 어댑터     Chat / 기타 활동
         관찰·입력·원본 기록    관찰·입력·원본 기록   사용자와의 대화
```

- 새 게임을 붙이는 비용 = 그 게임의 어댑터 하나 + Activity Context 하나. Persona 코어는 바뀌지 않는다.
- 게임마다 쌓이는 것과 게임을 넘어 쌓이는 것을 나눈다. 이 구분이 "다른 경험이 계속 쌓인다"를 가능하게 한다(3절).

## 0. 플레이 프로세스와 Persona 완성도의 분리 (사용자 결정 2026-10-21)

Persona의 추론·기억 구조(History 설계)가 얼마나 완성되었는지가 게임을 플레이할 수 있는지를 좌우하면 안 된다. 완성도는 플레이 실력에 영향을 줄 수 있지만, 둘은 별개의 관계로 다룬다.

이를 위해 경계를 하나 고정한다.

```text
환경 어댑터 ──(Agent Event, 단계 경계 입력)──▶ ┌ 플레이어 인터페이스 (고정) ┐
            ◀──(행동 Proposal, 대기 조건)────── │                         │
                                               └──────────┬──────────────┘
                                                          │ 뒤의 구현은 교체 가능
                                     v0: 단일 모델 호출 + 단계별 문맥 틀, 기억 없음
                                     이후: v5 Cognition, Recall, Self·Relation …
```

- **플레이 프로세스**(Foundation과 어댑터의 일): 사건 받기, 정지 중심 진행, 모델 호출과 도구 실행의 반복, 단계 경계 입력 주입, 행동 실행, 원본 기록. 이것은 Persona 내부가 비어 있어도 돌아간다.
- **Persona 내부**(Agent Plane의 일): 문맥에 무엇을 넣을지, 무엇을 떠올릴지, 어떻게 판단할지. 플레이어 인터페이스 뒤에서 언제든 바뀐다.
- **경험은 처음부터 남긴다.** 기억 구조가 없어도 Persona가 겪은 Experience Stream(받은 사건, 명시적 행동, 결과, 개입)은 플레이 첫날부터 저장한다. 나중에 Memory Formation이 생기면 이 Stream을 거슬러 형성할 수 있다. 원본 게임 로그(System History)에서 기억을 자동으로 만들지는 않는다는 v5 원칙과도 맞는다. 그렇게 하지 않으면 기억 구조가 생기기 전의 플레이는 Persona에게 없던 일이 된다.
- **영향은 관찰 가능하게 한다.** 각 플레이 구간에 그때 켜져 있던 Persona 내부 구성(모델, 모듈 버전)을 Structural Fact로 함께 기록한다. 그러면 완성도와 실력의 관계를 섞지 않고 나중에 비교할 수 있다.

이 결정으로 4절 단계의 의존 관계가 바뀐다. M1은 v5 Cognition 없이 시작하고, M2·M3은 플레이를 막지 않는 별도 흐름이 된다.

## 1. 세 가지 자산과 각각의 주인

| 자산 | 주인 | 성격 | 유지보수 원칙 |
|---|---|---|---|
| Persona 상태 (기억, 자기 해석, 관계, 활동 해석) | AI_Persona_Pre | 대체할 수 없음. 이 개체의 역사 | 백업, 순방향 마이그레이션, 원본 불변, 위험한 변경 전 스냅샷 |
| 환경 어댑터 (Lobotomy 등) | 환경별 저장소 | 교체 가능한 도구 | 게임 패치·UI 변경에 따라 고침. Persona 상태를 갖지 않음 |
| Environment Contract | Persona 저장소에 정본 | 둘을 잇는 약속 | 버전 번호, 하위 호환, 변경 시 양쪽 테스트 |

가장 중요한 것은 첫 줄이다. 코드는 다시 쓸 수 있지만 Persona의 경험사는 다시 만들 수 없다. 유지보수 체계의 중심을 여기에 둔다.

## 2. Environment Contract에 들어갈 것

Lobotomy가 이미 지키는 원칙을 일반화한 것이다. 처음에는 Lobotomy 하나만 보고 만들되, 게임 고유 용어는 넣지 않는다.

| 항목 | 내용 | Lobotomy의 현재 대응물 |
|---|---|---|
| 환경 설명서 | 이름, 무엇을 하는 곳인지, 시간축(정지 가능 여부, 배속), 에피소드 경계(일차·시도 등), 선택의 기원(사용자가 정함/스스로 고름) | `config/player/AGENTS.md`의 일부, Run·일차 정의 |
| 공개 범위 | 플레이어가 정당하게 볼 수 있는 정보만 내보낸다는 선언과 검사 | ConsoleDisclosure |
| 관찰 | 현재 상태 요약, 변경분, 사건, 이미지 요청 | observe, delta, view_region |
| 행동 | 의도 단위 행동 Proposal과 실행 영수증. 전송은 성공의 증명이 아님 | execute_intents, 영수증 |
| 대기 | 에이전트가 고른 조건으로 깨우기, 일회용 정지 예약 | wait_for_event, arm_pause |
| 원본 기록 | 환경 쪽 원본 사실. Persona 기억이 아님 | `.robotomy/live`, 경험 원장 |
| 사람 개입 | 사용자가 직접 조작한 사실의 기록 | 개입 기록 |
| 에피소드 경계 신호 | 일차 종료처럼 기억 형성을 깨울 수 있는 기계적 전이 | 일차·시도 경계 |

**일반화 시점:** 공통 라이브러리를 지금 뽑아내지 않는다. 두 번째 환경을 붙일 때 실제로 겹치는 것만 꺼낸다. 하나만 보고 만든 추상화는 대개 틀린다.

## 3. 게임마다 쌓이는 것, 게임을 넘어 쌓이는 것

| 층 | 범위 | 예 |
|---|---|---|
| Activity Context | 환경별 | Lobotomy 플레이북, 환상체 인상, 직원 평가. 다른 게임에 섞이지 않음 |
| Episodic Memory | 전체 | "13일차에 계획을 고집하다 직원을 잃었다" 같은 사건 기억. 출처 환경을 표시 |
| Self Context | 전체 | "나는 위기에서 기존 계획을 오래 유지하는 편이다" 같은 자기 해석. 여러 환경의 근거가 쌓임 |
| Relation Context | 전체(대상별) | 사용자와의 관계. 게임 속 인물을 대상으로 둘지는 열린 질문 |
| Mission / Perspective | 전체 | Become a person 해석. 게임 경험이 근거 중 하나가 됨 |

전이 학습이 일어나는 곳은 Self와 Episodic이다. 게임 지식(Activity)은 그 게임에 머물고, 성향과 교훈이 다음 게임으로 넘어간다.
게임 속 역할(시설 관리자)은 Activity 안에만 두고 Self에 섞지 않는다.

## 4. 진행 단계

각 단계는 실제로 쓸 수 있는 결과를 낸다. History의 설계가 넓으므로, 지금 플레이에 필요한 것부터 만들고 나머지는 그 위에 얹는다.

| 단계 | 만드는 것 | 쓸 수 있게 되는 것 |
|---|---|---|
| M0 | Environment Contract v0 문서. 결합 검토 2절 대응표 + 위 2절 | 양쪽 개발의 기준 |
| M1 | 플레이 프로세스: 플레이어 인터페이스, 모델 호출·도구 실행 루프, MCP 클라이언트, 단계 경계 입력 주입(채팅·게임 사건), 정지 중심 진행, Experience Stream 저장. Persona 내부는 v0(단일 호출 + 문맥 틀). Lobotomy: 플레이용 도구 프로필 | **로컬 Persona가 Lobotomy를 플레이**. Persona 내부 완성도와 무관 |
| M2 (병행) | Memory Context 최소형: Experience Buffer, Formation(쌓인 Stream을 거슬러 형성 가능), Recall. Lobotomy Activity Context로 플레이북 이전 | 기억 소유권이 Persona로 넘어감. 플레이를 멈추지 않고 교체 |
| M3 (병행) | v5 Cognition, 게임 밖 시간의 회고, Self 해석 갱신, 미해결 관찰 회수(「트리거」) | 경험이 자기 해석으로 이어짐 |
| M4 | 두 번째 환경. 이때 Contract를 검증하고 공통 부분을 추출 | 다중 환경 Persona |
| M5 | 활동 선택의 자율성: 일과 통보 → 후보 중 선택 → 스스로 제안(「경험과 성장」 3절) | 생활하는 Persona |

M1이 가장 크다. 0절에 따라 M1은 Persona 내부 구조를 기다리지 않는다. M2·M3은 M1 이후 언제든 병행하며, 플레이어 인터페이스 뒤에서 교체된다.

**두 번째 환경 고르는 기준(M4):** Lobotomy와 성격이 다른 것이 Contract 검증에 좋다. 예를 들어 턴제이거나 텍스트 중심이라 비용이 싸고, 정지 개념이 다르고, 공개 범위 문제가 단순한 게임. 실시간 3D 게임은 어댑터 비용이 커서 첫 확장으로는 무겁다.

## 5. 유지보수 체계

1. **Persona 상태 보호:** 정기 백업, 마이그레이션 전 스냅샷, 원본 사건 불변, 정정은 새 기록. Persona 저장소의 기존 원칙(순방향 마이그레이션, fail-closed 복구)을 기억 저장소까지 넓힌다.
2. **개체 연속성 규칙:** 모델 교체, 모듈 교체, 대규모 기억 재형성은 Persona에게 Structural Fact 변경 사건으로 기록한다. 실험적 변경은 복제본에서 먼저 한다. 복제본은 다른 개체로 취급한다(「인격과 의식」 8절).
3. **회귀 시험:** 환경마다 원본 기록에서 고른 장면 묶음을 두고, Persona 쪽 모듈을 바꿀 때 재생해 판단이 형식상 깨지지 않는지 확인한다. Lobotomy는 기존 Codex 플레이 기록을 첫 묶음으로 쓸 수 있다.
4. **관찰:** Research Inspector를 Cognition 단계·도구 호출·기억 형성까지 볼 수 있게 넓힌다. 유지보수와 연구가 같은 도구를 쓴다.
5. **문서 권위:** 결합 방향과 Contract의 정본은 Persona 저장소에 둔다(주체가 Persona이므로). Lobotomy 문서는 그것을 참조한다. 지금의 이 조언 문서들은 그곳으로 옮겨 정리할 초안이다.

## 6. 위험

- **범위 폭발:** History 설계를 한꺼번에 구현하려 하면 플레이가 계속 미뤄진다. 각 단계가 실제 플레이나 경험 축적으로 이어지는지를 기준으로 자른다.
- **하드웨어:** 게임과 Persona가 GPU를 나눠 쓰는 한계는 그대로다. 환경이 늘어도 동시에 하나만 플레이하는 것을 기본으로 한다.
- **기억 오염:** 엔지니어링 점검, 테스트 플레이, 사람 개입이 Persona 기억으로 새지 않게 Contract에서 표시한다. Lobotomy가 이미 이 구분을 한다.
- **저작물:** 게임 자산과 원본 영상은 저장소에 넣지 않는 기존 원칙을 Persona 기억 저장소에도 적용한다.

## 7. 다음에 할 일

1. M0 Contract v0 초안을 Persona 저장소의 Proposed 문서로 만든다(Codex 작업, 사용자 승인 후).
2. 앞 문서의 자원 측정(게임 정지·전투 시 VRAM/CPU)과 기록 재생 시험을 M1 준비로 진행한다.
3. M1의 Persona 쪽 작업 패킷을 Persona 저장소 절차에 맞게 쪼갠다.
