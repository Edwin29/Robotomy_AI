# diff/판단 비용 조사 — 2026-10-20

상태: 조사 및 설계 제안. diff 최적화는 아직 구현하지 않음. 기존 경고 선두 표시 패치와 구별한다.

## 실제 기록에서 확인한 사실

로컬 SQLite 경험 원장을 read-only로 조사했다. 숫자는 ensure_ascii=False, 공백 없는 JSON 문자 수이며 토큰 수가 아니다.
최근 구간 seq>=9000에서 관찰 18건: delta 9건(중앙값 27,925자), selection_changed full 9건.
같은 구간 입력 결과 439건의 중앙값 11,652자. 더 오래된 150건에는 이전 패치 버전이 섞여 있어 현재 성능으로 일반화하지 않는다.

호박빛 여명 사례 seq10811, UTC 2026-10-19 15:28:08:
- 전체 31,416자; change_summary 21,400자; audio_delivery 9,125자.
- diff 기준 seq10686은 15:23:07. 그 사이 action_result_offered가 27회 있었지만 기준은 갱신되지 않았다.
- 시설 33개 목록 5,886자. ID별로 비교하면 목록 이탈 4개, 수정 3개뿐이다. 변경 표현은 387자(실험적 재직렬화, 제품 구현 아님).
- 직원 5명은 모두 track_id가 바뀌어 단순 ID diff에서 삭제5/추가5가 된다. track_id는 지속 직원 ID가 아니라 추적 연속성에 의존한다.
- 소리 39건: start26, source_destroyed12, source_idle1. 중요 경고 외 식별자와 생명주기 메타데이터도 분량을 차지한다.
- seq10865는 selection_changed로 full, 59,880자. 옵션 변경 때문에 전체 지도 등을 다시 받는다.

지연 사례: UTC15:29:12 입력 결과→15:29:52 다음 입력 약40초;
15:29:53 결과→15:30:24 정지 입력 약30초. 해당 구간 입력 영수증20건 중앙313ms, 범위188~610ms.
관찰 도구 내부 대기0~15ms인 사례도 있었다. 이 기록만으로 모델 추론/호스트/전송 지연을 각각 분리할 수 없다.
JSON 축소율을 모델 속도 개선율로 주장하지 않는다.

## 제안 순서

1. 관찰과 입력 결과의 공통 반환 기준. 실제 반환한 필드만 기준에 포함하고 스키마/범위 차이를 관리.
2. 직원/엔티티/시설은 한 번만 표현. console.motion과 visible_employees/entities, raw UI와 구조화 창,
   priority_changes와 hazards 전체의 중복 제거. 원자료는 필요할 때 별도 조회.
3. 고정 시설은 ID별 추가/변경/현재 관찰에서 제외로 전송. 목록 제외는 파괴나 사망이 아니다.
4. 지속 식별자와 임시 추적/입력 토큰 분리. 내부 식별을 써도 비가시 현재 상태는 공개하지 않음.
5. 오디오는 짧은 공개 별칭/의미와 시각, 반복 묶기. 경고와 새로운 중요 소리는 유지.
   source_destroyed를 실제 들리는 정지로 단정하거나 미분류 소리를 무조건 버리지 않음.
6. 경고→대상별 변화→요청 시 상세의 순서. 시련 예고와 실제 출현을 구별.
7. 숫자 자릿수·카메라 공통 벡터 등 표현 축소는 그 다음. 벡터 자체를 제거하지 않음.

## 검증해야 할 것

실제 전투/정지/창 전환/카메라 이동/재등장/재연결 기록으로 전체 상태 재구성,
중요 신호 보존, 비가시 정보 철회, 최신 클릭 대상 검증을 확인한다.
원문 대비 문자/토큰 추정량, 응답 처리 시간, 관찰 간격, 최종 입력까지의 시간을 따로 측정한다.
5분 전 기준 문제와 공유 기준의 동시 호출 순서 문제를 함께 해결해야 한다.
진행 중 플레이를 실험에 쓰지 않는다. 별도 검증 환경에서 검증 후 배포한다.
