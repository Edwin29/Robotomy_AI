# 초 단위 플레이 개선안 (수정판) — 2026-10-20

작성: Claude (조언 역할). [이전 조언](claude-advice-realtime-latency-cost-20261020.md)을 대신한다.
바뀐 전제는 두 가지다. 플레이어는 Codex 데스크탑 앱을 쓰므로 하루 도중에 모델을 바꿀 수 없다.
그리고 플레이·판단·playbook 작성은 **한 모델(플레이 주체)**이 맡아야 경험의 주인이 유지된다.
그래서 모델 역할 분담(Luna 실행, Astra 계획)과 `ask_planner` 제안은 철회한다. 코드·설정은 바꾸지 않았다.

## 원칙

**판단은 한 모델, 속도는 도구에서 얻는다.** 지금 입력 처리는 약 0.3초인데 입력 사이 간격은 30~40초다.
시간 대부분이 모델이 긴 관찰을 읽고 생각하는 데 쓰인다. 따라서 할 일은 다음 셋이다.

1. 모델이 읽는 양을 줄인다.
2. 모델을 부르는 횟수를 줄인다.
3. 모델이 보지 않는 동안 일어난 일을 놓치지 않게 한다.

손발 역할의 도구는 플레이어가 정한 것만 실행하고 판단하지 않는다. 사람으로 치면 손에 익은 조작과 반사 신경이므로 플레이 주체는 바뀌지 않는다.

## 개선안 (순서대로)

### 0. 계측 (먼저, 위험 없음)

호출마다 모델 대기 시간, 도구 실행 시간, 응답 크기(토큰 추정)를 원장에 남긴다. 이후 모든 개선의 효과를 이 수치로 비교한다.
구독 사용량이 어디서 소모되는지도 이것으로 보인다(9일차 마지막 시도는 사용량 부족으로 중단).

### 1. 관찰 줄이기: 호출당 1~2천 토큰 목표 → 읽는 양

지금은 delta 중앙값 약 2.8만 자, full 약 6만 자다. Codex의 [최적화 조사](diff-optimization-audit-20261020.md) 방향에 두 가지를 더한다.

- **기본은 요약, 상세는 요청 시.** 기본 응답에는 경고, 직원별 상태 한 줄, 바뀐 것만 담는다. 방·환상체 상세는 `detail(...)`로 물을 때만 준다.
- **변하지 않는 것은 한 번만.** 지도, 규칙, playbook은 하루 시작 때 한 번 주고, 이후에는 바뀐 부분만 보낸다.
- 소리는 경고와 처음 듣는 소리만 남기고 반복은 묶는다. 생명주기 메타데이터(source_idle/destroyed)는 기본 응답에서 뺀다.

### 2. 기다리는 도구 → 놓침 방지 + 호출 감소

```
wait_for_event(timeout_s=20, on=[경고음, 새 알림/사망 로그, 보이는 HP가 정한 값 이하, 작업 완료, 시련 표시])
```

- 조건이 보이거나 시간이 다 되면 그때 돌려준다. 그동안 일어난 일은 시간순 목록으로 함께 준다.
- 기다리는 동안 모델은 토큰을 쓰지 않는다. 같은 시간을 반복 관찰로 채우는 것보다 훨씬 싸다.
- 조건은 플레이어가 고르고, 게임기는 화면에 표시된 정보가 조건과 맞는지만 확인한다.
- **결정 필요:** 조건이 맞으면 즉시 일시정지하는 옵션(`pause_on_trigger`)을 허용할지. 현재 “게임기 자동 일시정지 금지” 원칙과 겹친다.
  허용한다면 사람 수준의 반응 지연(예: 0.3~0.5초)을 넣고 실험 조건으로 기록하는 것을 권한다. 허용하지 않아도 깨우는 기능만으로 효과가 크다.

### 3. 의도 단위 행동 → 호출 감소, 조작 실수 감소

- 한 호출에 여러 의도를 받는다. 예: “에덴 애착 → O-09-91, 브룩 본능 → 대머리, 정보팀 전원 → 우하단 복도”.
- 각 의도를 실행하기 직전에 현재 화면에서 대상을 다시 확인하고, 안 보이거나 바뀌었으면 그 의도만 보류한다.
- 결과는 의도별로 화면에서 확인된 것과 안 된 것만 돌려준다. 성공을 단정하지 않는다.
- 9일차의 드래그 좌표 오입력, 옛 행 ID 거절 같은 실수가 줄어든다. 이미 있는 game_input, 행 배정, move_employee를 확장하는 방향이다.

### 4. “멈추고 생각하기” 플레이 규칙 → 성급함과 놓침 감소

플레이어 지침(config/player)에 다음을 권한다. 사람도 이 게임에서 똑같이 한다.

- 시련 예고·발생, 새 환상체 탈출, 사망·패닉, 계획에 없던 상황이 오면 **먼저 일시정지하고 판단한다.**
- 게임을 진행할 때는 반복 관찰 대신 `wait_for_event`로 기다린다.
- 하루 시작 전(준비 화면, 게임 정지 상태)에 오늘의 계획과 위기 대응 체크리스트를 playbook에 쓴다. 생각할 시간을 위기 순간이 아니라 준비 시간에 쓰는 것이다.

### 5. 비전은 필요한 곳만, 잘라서

- 구조화하지 못한 영역만 잘라 보낸다. 전체 화면보다 토큰이 적고 판독 오류도 줄어든다.
- 스토리, 새 환상체 외형, 보스 연출처럼 이미지가 본질인 장면은 정지 상태에서 본다.
- 반복되는 이미지 판정은 지금처럼 텍스처를 텍스트로 바꾸는 범위를 넓히는 게 가장 싸다.

## 모델과 비용

- 모델은 하나로 고정한다. 9일차 같은 저장 상태에서 위 개선 전후와 모델별(Sol light, Astra light)로 같은 시도를 반복해
  생존 수, 에너지, 입력 간격, 사용량을 비교하고 정한다. 개선 후에는 호출당 읽는 양이 줄어 비싼 모델의 부담도 같이 준다.
- 구독 대신 API를 쓰게 되면 하루 비용은 대략 `호출 수 × (입력 토큰 × 단가 + 출력 토큰 × 단가)`다.
  1번과 2번이 호출 수와 입력 토큰을 동시에 줄이므로, 어느 쪽을 택하든 먼저 할 일은 같다. 단가는 확인하지 않았다.

## 기대 효과와 한계

- 1~3번만으로 호출당 읽는 양과 호출 횟수가 크게 줄고, 위험 순간을 다음 관찰까지 기다리지 않게 된다(추정, 0번으로 확인).
- 그래도 LLM이 매 순간 반응하는 수준(0.3초)은 아니다. 초 단위 위기는 “일시정지 후 판단”으로 넘기는 게 이 구조의 전제다.
- 2번의 자동 일시정지 여부만 원칙 변경이 필요하고, 나머지는 현재 원칙 안에서 할 수 있다.
