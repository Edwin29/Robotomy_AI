# 화면 이동 벡터 장치 — 구현과 검증

2026-10-18 KST. 개발 검증 자료. 게임 공략이나 플레이어의 자전적 경험으로 가져오지 않는다.

## 제공 계약

`observe_live(max_items=16, motion_only=true)`는 화면 위치와 이동 벡터만 반환한다.
기존 전체 관찰·Obsidian checkpoint에는 같은 시각의 UI·소리 근거도 보관한다.
플레이어가 모든 PNG를 해석하거나 두 화면의 차이를 계산할 필요는 없다.
장치 실행에는 유료 API, LLM, 비전 모델, OCR을 사용하지 않는다.

| 필드 | 의미 |
|---|---|
| `track_id` | 연속해서 관찰된 동안만 유지되는 임시 ID. 이름·직원 ID·환상체 종류가 아님 |
| `position` | 실제 불투명 표면에 확인한 지점. 좌상단 원점, 오른쪽 +x, 아래 +y |
| `bounds` | 그 지점을 검증한 2×2px 영역. 전체 개체의 몸체 크기가 아님 |
| `screen_velocity` | 화면에서 보이는 총 이동, px/현실 초 |
| `object_velocity` | 현재 카메라 기준으로 계산한 대상 자체의 이동 |
| `camera_velocity` | 카메라 이동·확대·축소가 해당 지점에 만든 이동 |
| `interval_ms` | 두 표본 간 실제 시간 |
| `state` | `acquiring`, `tracking`, `discontinuity` |

각 축에 대해 `screen_velocity ≈ object_velocity + camera_velocity`다.
현재 카메라로 직전 표시 위치를 다시 투영하여 두 성분을 분리한다. 확대할 때 카메라 성분은
대상 위치마다 다르므로 하나의 공통 카메라 속도를 모든 대상에서 빼지 않는다.
이 값은 내부 이동 능력치나 목적지·경로가 아니다. 평균 변위이며 순간 가속도나 공격 모션 의미는 알려주지 않는다.
개체 표시 Transform 기준의 대표 이동이다. 팔다리별 애니메이션, 자세 변화, 공격 준비 동작을
모두 벡터로 표현한 것은 아니다. 그런 정보가 필요한 순간의 영상 관찰은 여전히 필요하다.

## 수집과 가림

Unity `WaitForEndOfFrame` 시점에 기존 UI 수집과 함께 약100ms 간격으로 계산한다.
작업자/환상체의 최종 표시 Transform, 실제 Spine 분할 메시, UV·정점 alpha·텍스처 alpha,
렌더러 상태, 카메라 범위·후처리, UI 및 앞쪽 렌더러를 검사한다.
매 표본 같은 로컬 표면 지점이 여전히 불투명하게 보이는지 재검사한다.
보이는 지점이 바뀌거나 대상이 사라지면 이전 속도를 이어 붙이지 않는다.

UI가 겹치면 보수적으로 제외한다. 일반 방 그림자처럼 위치를 왜곡하지 않는 알려진 월드
alpha 합성은 겹치는 텍스처 영역의 최대 alpha와 실제 tint로 투과율의 하한을 계산한다.
모든 앞쪽 레이어를 통과한 하한이50% 이상일 때만 표면을 허용한다. 불투명 가림은0%다.
초기70% 기준은 실제로 선명하게 보이는 직원도 정상적인 방 그림자 때문에 누락시켰다.
이50%는 장치의 허용 정책이며, 인간 인지의 보편적인 임계값을 측정한 결과가 아니다.
알 수 없는 shader를 임의로 이 규칙에 넣지 않는다.

- 새로 보인 대상의 속도는 `null`. 미측정을 정지 `0`으로 표현하지 않는다.
- 가림·화면 이탈 대상은 배열에서 제거하고 이전 추적 기록을 폐기한다. 재등장하면 새 ID다.
- 여러 렌더러로 분할된 몸체가 화면 경계에 걸친 경우에도 보수적으로 제외한다.
- 알 수 없는 후처리, 카메라 합성, shader, 투명도·텍스처 조건은 정보를 보류한다.
- 구조화 관찰 자체의 기존 TTL은750ms이지만 이동 벡터는250ms를 넘기면 독립적으로 만료한다.
- `available`인데 빈 목록이어도 화면에 개체가 없다는 뜻은 아니다. 안전하게 확인한 표면이 없다는 뜻이다.

현재 승인 범위는 이 PC의 게임 빌드와 **Tutorial_1의 검증한 일반 렌더 설정**이다.
`config/motion-render-profile.txt`는 알려진 효과의 필드 값을 명시한다. 실행 중 설정을 자동 승인하지 않는다.
새 설치 준비 시 알려진 게임 어셈블리 SHA256일 때만 이 설정을 복사하며 기존 로컬 설정은 덮어쓰지 않는다.
다른 씬·보스전·화면 왜곡은 아직 승인하지 않았으므로 `withheld`를 반환한다.

텍스처 alpha는 씬별로 캐시하며 prefix sum 메모리는64MiB, 텍스처256개로 제한한다.
prefix 두 개와8×8 texel 구역별 최대 alpha 배열을 모두 메모리 한도에 포함한다.
동적인 렌더 메시 데이터는 프레임별로만 캐시한다. 작은 영역의 alpha 확인은 상수 시간 연산이며,
비전 추론을 대신한다. 지역 최대 alpha는 겹치는 작은 구역을 확인하는 연산이다.
확대가 너무 작아 불투명 표면을 증명하지 못하면 누락될 수 있다.
정상 생성된 mip chain과 씬 중 불변 텍스처라는 승인 프로필의 조건을 전제로 한다.
임의 모드로 변경된 shader/asset, 모든 보스 효과에 대한 픽셀 가시성 증명은 아니다.

## 검증 방법

`scripts/motion_trial.py`는 시간 제한을 둔 가상 입력과 실제 관찰을 기록한다.
PNG는 SHA256과 같은 `unity_frame`의 관찰을 `frame-motion.json`으로 연결한다.
`scripts/analyze_motion.py`는 저장된 이미지의 특징점 변위를 OpenCV로 독립 대조한다.
OpenCV는 선택적인 **오프라인 검증 도구**이고 게임기나 플레이어 실행 의존성이 아니다.
숫자의 분해 항등식 확인과 이미지 대조는 별개의 증거로 기록한다.

`MotionProbe`는 실제 튜토리얼 위에 임시 가림/후처리를 적용하는 개발 시험이다.
게임 진행·모델·저장 데이터를 조작하지 않으며 종료 시 렌더 상태를 복원한다.
이 시험 동안 공개 motion은 보류된다. 원래 플레이 경험과 합성 시험을 혼동하지 않는다.

각 가림 시험의 실제 렌더 화면도 `motion-probe-<case>.png`로 남긴다. 불투명 UI, 반투명 UI,
불투명 월드 스프라이트, 옅은 방 그림자, 스텐실 마스크, 카메라 컬링, 렌더러 비활성,
알 수 없는 후처리와 승인 후처리 설정 변경을 나누어 확인한다. 투명 픽셀도 스텐실을 쓸 수
있으므로 alpha가0인 스텐실 writer를 별도 반례로 둔다.

## 구현 과정에서 발견한 문제

- `SpriteRenderer`는 일반 상태에서도 내부 MaterialPropertyBlock을 사용했다. 블록 존재만으로
  제외하던 방식 대신 검증한 shader의 실제 속성 경로를 확인했다.
- 방의 옅은 그림자는 완전 투명하지 않다. alpha0 검사만으로는 정상적으로 보이는 직원도
  제외되므로, 지역 alpha 상한으로 투과율 하한을 계산하도록 바꿨다.
- 방 배경의 사각형은 직원과 겹치지만 스텐실 검사를 통과한 부분만 실제로 그려진다.
  스프라이트의 실제 삼각형과 스텐실 값을 쓰는 순서를 확인해야 했다.
- 중첩 UI Canvas의 로컬 renderMode만 읽으면 다른 카메라/루트의 UI 마스크를 월드 마스크로
  잘못 취급할 수 있다. rootCanvas를 함께 확인한다.
- 작업 지시 전후에 UI 정렬 순서가 바뀌었다. 정지 화면의 성공만으로 보행 검증을 대신하지
  않고, UI 마스크가 실제로 쓸 수 있는 스텐실 비트와 pop-material의 복구 동작까지 확인한다.
- 첫 후보 지점이 가려져 있다고 몸체 전체를 버리지 않고, 같은 몸체의 다른 불투명 표면도
  검사한다. 기존 지점이 계속 보이면 재사용하여 계산량과 추적 단절을 줄인다.
- 두 차례 실행은 Intro에서 새 관찰을 게시하지 못했다. 오래된 관찰로 입력하지 않고
  해당 private PID를 확인한 후 종료·재실행했다. 이 실행은 성공 측정에서 제외한다.
  시작 스크립트도 Intro 관찰 하나로 준비 완료를 선언하지 않고, 제한 시간 안에 타이틀 등
  다음 씬의 새 관찰이 도착해야 성공하도록 보완했다.

초기 빈 목록은 안전성이나 기능 성공의 증거로 세지 않는다. 양성 추적과 의도적인 가림
음성 사례를 함께 통과해야 한다. 실행 중 수집한 엔진 이름·shader 진단은 개발 폴더에만
보관하고 플레이어 응답은 Python의 명시적 필드 허용 목록을 통과시킨다.

## 렌더링 경로 재검토와 공통 수정

반복 시험에서 보이는 직원까지 누락되는 문제가 있어, 버전별 양성 결과를 최종 완료로
간주하지 않는다. v19는 정지·카메라 이동과 13개 가림 시험을 통과했지만 실제 작업 명령
이후 추적이 모두 사라졌다. v20은 UI 스텐실 비트 쓰기/복구를 추가했으나 정지 화면에서도
추적이 누락되어 채택 조건을 충족하지 못했다. 과거 시험 JSON은 수정하지 않는다.

게임 파일을 다시 추적한 근거:

- `Tutorial.DefaultState.SaveDefaultState`는 UI Canvas를 UI 레이어/3010 또는4010으로
  올리고, `BackToDefault`와 `CompleteTutorial`은 이전 레이어와 순서로 되돌린다.
  `.robotomy/analysis/Assembly-CSharp.decompiled.cs:251800` 이후에 해당 경로가 있다.
  단계가 바뀔 때 UI 정렬이 달라지는 것은 정상 게임 동작이다.
- 게임에 포함된 `UnityEngine.UI.dll` SHA256은
  `d6925513e19634dd3872abe83367690b87d64bee00cf2ef3e197dced056f7312`다.
  `Graphic.DoMeshGeneration`/`DoLegacyMeshGeneration`은 모든 `IMeshModifier` 처리 후
  `CanvasRenderer.SetMesh(workerMesh)`를 호출한다.
  `.robotomy/analysis/ui-geometry/UnityEngine.UI.Graphic.decompiled.cs:399` 이후에 있다.
  이 최종 메시 경로는 UI 영역을 추측하는 대신 실제 제출 도형을 읽을 수 있는 후보다.
- 게임의 `SkeletonGraphic`은 별도로 `CanvasRenderer.SetMesh`를 호출한다. 일반 Graphic
  경로를 후킹해도 모든 사용자 정의 UI를 포괄했다고 가정하면 안 된다.

초기 가설은 미지원 UI의 영역을 화면 전체로 과대평가한 것이었다. v21의 최종 도형 수집은
모든 UI writer를 오류 없이 읽었지만 문제를 해결하지 못했다. 실제 입력용 UI 자체가 매우
큰 경계상자를 가지고 있었다. 이후 게임의 Image 설정과 도형 생성 경로를 함께 추적했다.

`UnitMouseEventManager`의 Image는 `Sliced`, `fillCenter=false`다. 참조 Sprite는
`resources.assets:10127`, border=(10,10,10,10)이다. 게임에 포함된
`Image.GenerateSlicedSprite`는 이 설정에서 중앙 사각형을 만들지 않는다. 따라서 큰
경계상자 안에 직원이 있다는 이유로 스텐실 쓰기가 겹친다고 판단하면 틀린다.
알파0이라는 별도 가설도 채택하지 않았다. 실제 Image 색은 alpha1이고 텍스처 전체도
완전 투명이 아니었다. 정적 근거는 `.robotomy/analysis/ui-stencil-center-hole-audit.json`에 있다.

최종 구현은 `MotionCanvasGeometry`에서 게임이 제출한 최종 정점과 삼각형을 읽는다.
카메라·변환별로 투영한 삼각형과 2×2px 관측 영역의 실제 겹침을 검사한다. 글자나 그림자 등
메시 수정 이후 결과이며, 게임의 도형 생성 규칙을 장치에서 다시 구현하지 않는다.
지오메트리 배열 캐시는16MiB로 제한하고 dirty/disable/scene unload 시 폐기한다.
미수집·미지원 도형은 보수적으로 처리한다. 오브젝트 이름별 통과 예외는 없다.

v22 실제 실행에서 입력용 UI의16개 삼각형은 화면 중앙과 겹치지 않았다. 같은 화면의
3개체가 정상 추적됐고, 작업 지시 후 UI 정렬 복원에서도 추적이 유지됐다.
`motion-canvas-writers.json`의 당시 UI 캐시는81,488bytes, 수집 실패0이었다.
이 내부 이름·캐시 진단은 플레이어 응답에 포함하지 않는다.

보행의 비영 영상 대조는 **1건**이다. 영상 특징점에는 보행 애니메이션에 따른 상하 흔들림도
포함된다. 위 수치는 해당 구간의 대조 결과이며, 전 개체·모든 방향·모든 스테이지에 대한
정확도나 오류 상한이 아니다. 특징점 대응을 확보하지 못한 구간은 건너뛴 수를 원본 분석에
기록했다. 장시간 보행·회전/배속·문/엘리베이터·보스전은 추가 검증 대상이다.

| 장치 비용 | 정지 | 실제 작업 지시 구간 |
|---|---:|---:|
| 벡터 계산 중앙값 /95백분위 | 11.15/13.70ms | 9.01/11.54ms |
| 실제 표본 간격 중앙값 /95백분위 | 111.21/118.44ms | 103.85/118.53ms |
| PNG 캡처 중앙값 | 84.49ms | 85.31ms |

장치가 약100~120ms마다 표본을 만든다는 뜻이며 LLM이 그 속도로 판단한다는 뜻은 아니다.
PNG의 메인 스레드 비용과 최초 텍스처 캐시 구축 지연은 남아 있다. 기존 PNG 경로까지
실시간 제어에 충분히 최적화했다고 주장하지 않는다. motion-only 실제 MCP 응답은 이번
1개체 시점에 UTF-8 JSON 약1.2KB였고, 게임기 실행에서 비전 모델/OCR/유료 API를 호출하지 않았다.
