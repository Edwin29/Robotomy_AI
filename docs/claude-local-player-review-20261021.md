# 로컬 플레이어 도입 검토 — Claude 의견 (2026-10-21)

작성: Claude (조언 역할). 대상: [로컬 모델 검토용 현황](local-model-review-20261021.md).
코드·설정·게임은 건드리지 않았다. 새로 한 일은 기존 Codex 플레이 기록(rollout JSONL)을 **읽기만** 해서 수치를 뽑은 것이다.
모델 추론·설치·게임 조작은 하지 않았다.

## 결론 먼저

1. **지금 근거로는 "로컬 모델로 플레이어를 교체"를 추천할 수 없다.** 현재 플레이어가 실제로 쓰는 문맥은 중앙값 약 20만 토큰이고,
   첫 호출만 약 3.8만 토큰이다. 이 PC의 8GB GPU(게임이 이미 약 3.4GB 사용)에서 돌릴 수 있는 모델·문맥과 자릿수가 다르다.
2. **비용 문제의 1차 원인은 모델 단가보다 "한 세션을 며칠 이어 쓰는 구조"로 보인다.** 같은 모델(Sol)을 유지한 채
   일차 단위로 세션을 끊고 짧은 인계 묶음으로 시작하면, 판단 모델과 정체성을 바꾸지 않고 소모를 줄일 여지가 크다. 이것을 먼저 시험하길 권한다.
3. **로컬 모델은 "판단하지 않는 부품"으로만 먼저 검토할 가치가 있다.** 판단을 나누면 사용자가 원하는 "한 모델이 판단하는 플레이어"가 깨진다.
   이 점에서 내가 10-20에 낸 계획/실행 모델 분리안([이전 조언](claude-advice-realtime-latency-cost-20261020.md) ④)도 철회한다.

## 1. 새로 측정한 사실 (기존 문서의 "미측정" 항목 일부)

출처: `~/.codex/sessions/2026/10/18/rollout-2026-10-18T13-58-54-….jsonl` (작업 폴더 `Robotomy_Player`, 모델 `gpt-6.1-sol`, 2.67GB).
Codex가 호출마다 남기는 `token_count` 이벤트(3,427건)와 `rate_limits` 필드를 읽었다. 5MB 이상 rollout 중 `Robotomy_Player`를 작업 폴더로 가진 것은 이 하나였다.

| 항목 | 값 |
|---|---|
| 기록 구간 | 2026-10-18 ~ 10-21, 벽시계 68.8시간 / 호출 간격 5분 미만만 합친 활동 시간 약 18.5시간 |
| 모델 호출 수 / 도구 호출 수 | 3,427 / 3,361 (그중 3,328건이 Codex 코드 실행형 도구 호출) |
| 호출당 입력 문맥 | 첫 호출 38,202 · 중앙값 198,952 · P90 382,342 · 최대 443,286 토큰 |
| 문맥 압축 | 25회 |
| 누적 입력 / 캐시 비율 | 7억 3,370만 토큰 / 98% 캐시 |
| 누적 출력 / 추론 출력 | 58만 / 9만 토큰 |
| 호출 간격 | 중앙값 16초, P90 34초 |
| 이미지 포함 기록 줄 | 1,895줄 |
| 주간 한도(`primary`, 10080분 창) | 10-18: 4%→100%, 10-19: 0%→93%, 10-20~21: 10%→63% |

해석과 주의:

- 하루 플레이가 주간 한도 대부분을 쓴다. 다만 `rate_limits`는 계정 전체 값이라 같은 시간의 개발용 Codex 세션 사용분이 섞여 있다. 플레이어 몫만 분리하지 못했다.
- 캐시 비율이 98%여도 매 호출이 20만 토큰 규모를 다시 읽는다. 캐시된 입력이 한도에서 얼마로 계산되는지는 공개 근거를 확인하지 않았다.
- 중앙값 16초 간격은 모델 생각 시간만이 아니다. 도구 실행·대기(`setTimeout`)가 섞여 있다. `scripts/analyze_play_latency.py`로 분리할 수 있다.
- 첫 호출 3.8만 토큰은 지침·도구 정의·페르소나만으로 생긴다(`config/player/AGENTS.md`만 49KB). 로컬 모델에는 이 고정분부터 부담이다.

## 2. 기존 검토 문서에서 부족한 근거

| 부족한 점 | 왜 중요한가 | 채우는 방법 |
|---|---|---|
| 비용의 원인 분해가 없다 | 원인이 "긴 세션 문맥"이면 모델 교체 없이 해결된다 | 위 rollout에서 일차별 호출 수·문맥·한도 증가를 묶어 본다. 개발 세션과 시간대를 분리한다 |
| "로컬로 옮기면 싸진다"의 비교 대상이 없다 | 로컬은 금액 대신 품질·지연·게임 성능을 낸다 | 같은 장면 묶음에서 Sol과 로컬 후보의 판단을 오프라인 비교한다 |
| 정체성 요구와 구성안의 충돌이 정리되지 않았다 | 8번 질문의 "역할별 분리·복수 모델"은 사용자가 원하는 단일 판단 모델과 충돌한다 | 판단을 하는 부품과 하지 않는 부품을 먼저 정의한다(3절) |
| 호스트 의존성이 과소평가됐다 | 현재 플레이어는 도구를 거의 전부 Codex 코드 실행형 호출로 묶어 쓴다. LM Studio는 이것이 없다 | 로컬 호스트에서 같은 일을 하려면 호출 수가 늘거나 MCP 쪽에 묶음 도구가 필요하다. 압축 전 정지 훅·공개 채팅 수집도 Codex 전용이다 |
| GPU 적재 가능성이 계산되지 않았다 | 게임 사용 3.4GB 뒤 여유 약 4.5GB. 8B Q4 가중치(파일 6.19GB, 비전 포함)는 GPU에 다 올라가지 않는다 | 일부 CPU 오프로드 시 속도 저하와 함께 게임의 CPU 병목을 직접 건드린다. 4단계 동시 실행 측정 전에는 판단 불가 |
| 긴 프롬프트 첫 처리 시간 | 4060에서 수만 토큰을 매번 처음부터 읽으면 응답 전 대기가 수십 초가 될 수 있다(추정, 미측정) | 짧은 고정 프롬프트 + 문맥 캐시 재사용 조건에서 첫 토큰 지연을 측정한다 |
| 10-17 실험 계획과의 관계 | 그 계획은 "후보 중 하나를 고르는 선택기"를 시험한다. 지금 질문인 "플레이어 전체 교체"와 다르다 | 둘을 섞어 해석하지 않는다 |

## 3. 대안과 평가

정체성 기준: "누가 판단했는가"가 한 모델로 유지되는가.

| 안 | 내용 | 비용 | 지연 | 정체성 | 판단 |
|---|---|---|---|---|---|
| A. 일차 단위 세션 교대 | Sol 유지. 일차 시작마다 새 세션, 페르소나·플레이북·전날 회고·현재 상태표만 담은 인계 묶음으로 시작 | 문맥 20만→수만 토큰대로 줄 가능성(추정) | 짧은 문맥이라 오히려 빨라질 수 있음 | 유지. 기억은 출처 있는 기록으로 이어짐 | **먼저 시험** |
| B. 고정 프롬프트 다이어트 | `config/player/AGENTS.md`·도구 설명을 플레이 중 필요한 것과 회고용으로 나눔 | 매 호출 고정분 감소 | 소폭 개선 | 유지 | A와 함께 |
| C. 판단 없는 로컬 부품 | 이벤트 대기·조건 깨우기(코드), 소리 반복 묶기, 텍스트 검색(임베딩 또는 전문 검색) | 클라우드 호출 수 감소 | 대기 중 토큰 0 | 유지. 무엇을 할지는 Sol이 정함 | A 이후 |
| D. 로컬 단독 플레이어 | Qwen3-VL-8B 등이 전부 판단 | 금액 0, 전력·성능 비용 | 미측정, 불리할 가능성 큼 | **다른 플레이어가 됨** | 교체가 아니라 별도 플레이어 실험으로만 |
| E. 로컬 실행 + Sol 계획 (이전 내 제안) | 작은 모델이 계획 안의 단계를 수행 | 감소 | 개선 | 실행 중 선택이 섞여 귀속이 흐려짐 | 사용자 요구와 충돌, 보류 |
| F. 종량 API로 Sol급 사용 | 구독 대신 과금 | 위 누적 입력 규모면 3만원 상한과 맞지 않을 가능성 큼(단가 미확인) | 같음 | 유지 | A로 줄인 뒤 다시 계산 |

C에 넣을 부품의 경계: 결과가 "무엇을 할지"를 바꾸는 요약·선별·우선순위 판정은 판단으로 본다. 그런 일을 로컬 모델이 하면 E와 같은 문제가 생긴다.
기억 검색도 무엇을 꺼내 줄지가 판단에 영향을 주므로, Sol이 질의어를 고르고 검색기는 출처와 함께 결과만 돌려주는 형태가 안전하다.

## 4. 권하는 순서 (모두 사용자 승인 뒤, 구현은 Codex)

1. **기존 기록 재분석(위험 없음).** 이 rollout을 일차·시도 경계로 나눠 호출 수·문맥·한도 증가를 표로 만든다. 같은 시간대 개발 세션 rollout도 읽어 플레이어 몫을 분리한다. 문맥에서 도구 결과·이미지·지침이 각각 차지하는 비율도 뽑는다.
2. **A+B 한 일차 시험.** 같은 Sol 설정으로 새 세션 + 인계 묶음으로 하루를 진행하고, 1과 같은 지표로 비교한다. 인계 묶음이 놓친 사건이 판단을 틀리게 했는지도 회고에 남긴다.
3. 그래도 한도가 부족하면 C를 하나씩 넣는다.
4. 로컬 모델을 계속 보고 싶다면, D를 "두 번째 플레이어"로 따로 귀속해서 짧은 오프라인 장면 비교부터 한다. 이 결과는 현재 플레이어의 대체 근거로 쓰지 않는다.

## 5. 사용자가 정할 것

- 판단 모델 하나 원칙에서 "판단"의 범위: 기억 검색 결과 선별, 관찰 요약을 판단으로 볼지.
- 일차 단위 세션 교대를 플레이어 경험의 연속성 측면에서 받아들일지. (Run 정의는 바뀌지 않는다. 새 채팅은 새 Run이 아니다.)
