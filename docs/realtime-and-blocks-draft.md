# 실시간 관측과 제한된 입력 블록 검토 초안

기록일: 2026-10-18. 상태: 임시 검토 문서, 구현 지시 또는 확정 사양이 아님.

**이후 상태:** 사용자 지시로 스크래치형 블록 실행기 구현은 보류했다. 먼저 기존
가상 입력으로 플레이 성능을 확인한다. 객체 표시 경로 확장과 개수 기반 버퍼는 구현했으며,
현재 계약·검증 범위는 [최근 관측 버퍼](live-history.md)와 [인계 기록](handoff.md)을 따른다.
아래 블록 논의는 후속 검토용이며 구현 완료나 자동화 권한을 의미하지 않는다.

사용자는 실제 플레이 경험을 근거로 초 단위 반응이 거의 필수라고 확인했다.
LLM이 매 입력을 직접 결정하는 경로만으로 후반을 감당한다고 가정하지 않는다.
게임기는 관측·입력·기억 장치를 제공하고, 플레이어가 판단한다는 경계는 유지한다.
이 문서는 직전의 비동기 관측 검토와 사용자의 제한된 블록 자동화 제안을 함께 보존한다.

## 사용자 요구와 아직 정하지 않은 부분

- 초 단위 반응을 필수 설계 조건으로 취급한다. 허용 지연의 정확한 수치는 장면별로 측정한다.
- 숙련 뒤 기계적으로 반복하는 행동은 플레이어가 설정한 단순 논리 블록으로 실행할 수 있어야 한다는 제안이다.
- 반복 클릭, 카메라 이동 등이 예시다. 모든 플레이를 자동화할 정도로 무제한 허용하지 않는다.
- 블록 종류와 사용 개수를 제한한다. 화면 밖 또는 현재 인터페이스로 조작할 수 없는 대상을 클릭해서는 안 된다.
- 블록 하나의 종류와 기능을 고정하고, 연결해서 절차를 만든다. 주기·조건·키 입력·횟수 제한을 기본으로 삼으며 앞서 논의한 클릭도 단순 입력으로 유지한다.
- 총 블록 한도는 사용자가 변경하는 설정으로 둔다. 사용자가 플레이와 시행착오를 지켜보고 부족하다고 판단하면 늘린다. 자동 승급이나 고정 해금 조건은 두지 않는다.
- 블록과 고속 캐시는 지금 구현하지 않는다. 초기 총개수와 아래 주기·용량·유효시간은 미정이다.

## 현재 구현에서 확인한 관측과 입력 흐름

관측 생산은 AI의 읽기·추론 완료를 기다리지 않는다. Unity의 프레임 끝에서 약100ms 간격을
목표로 UI·수치·벡터를 수집한다. PNG는 약1초 간격이다. 파일 쓰기는 별도 스레드에서 수행한다.
그러나 UI·벡터 계산과 화면 읽기·PNG 인코딩 자체는 게임의 메인 스레드에서 수행한다.

| 자료 또는 경로 | 현재 상태 | 영향 |
| --- | --- | --- |
| 최신 UI·벡터 | latest.json 덮어쓰기 | AI가 읽지 않은 중간 변화는 보존되지 않을 수 있음 |
| 화면 | 최신 PNG와 프레임 메타데이터 덮어쓰기 | 연속 영상 이력은 없음 |
| 소리 | 최근 이벤트와 별도 누적 로그 | 재생 상태 근사이며 최종 혼합 파형 판독은 아님 |
| AI의 관찰 기록 | observe 호출 때 원장·Obsidian 노트 생성 | 고주기 읽기에 동기 저장 비용이 붙음 |
| 파일 게시 | 최대64개 선입선출, 가득 차면 새 항목 폐기 | 적체 시 최신 자료가 늦어지거나 누락될 수 있음 |
| 입력 도구 | 조작 완료 응답까지 동기 대기 | 설치된 FastMCP의 직접 동기 호출 경로에서 같은 서버의 요청 처리를 지연시킬 수 있음 |
| 가상 장치 | Unity Update에서 제스처 진행 | AI가 생각하는 동안에도 게임·수집은 진행됨 |

입력마다 원본 세이브 검증용 별도 프로세스를 실행하는 비용도 있다. 빠른 경로를 설계할 때
측정해야 하며, 속도 때문에 기존 세이브 보호를 제거하는 해법은 채택하지 않는다.

이전 Tutorial_1 실측은 벡터 계산 중앙값 약9~11ms, 표본 간격 약100~120ms,
PNG 캡처 약85ms였다. 이번 문서 작성 중 새 실측은 하지 않았다. 적은 수의 개체 결과를
후반 대규모 시설의 성능 보장으로 사용하지 않는다.

## 환상체와 시련의 이동 추적

게임의 CreatureLayer.AddOrdealCreature는 시련 모델을 CreatureUnit에 연결한다.
ChildCreatureUnit도 CreatureUnit을 상속한다. 현재 ConsoleMotion은 WorkerUnit과
CreatureUnit을 모두 후보로 모으므로 공통 표시 경로를 재사용할 수 있다.

다만 현재 후보는 특정 Spine 몸체 표시 경로에 한정되고, 추적 상한은128개이며,
승인 렌더 설정은 검증된 Tutorial_1 범위다. 시련 전 종류의 지원을 검증한 상태가 아니다.
ProjectileUnit, 별도 MonoBehaviour의 레이저·투사체·특수 효과에는 추가 표시 어댑터가 필요하다.
몸체 이동 벡터는 팔다리 움직임이나 공격 준비 자세를 설명하지 않는다.

확장 시 내부 정체·목적지·공격 대상·숨은 능력치를 내보내지 않는다. 최종적으로 보이는
표면의 익명 추적 ID, 위치, 범위, 화면/대상/카메라 속도를 제공한다. 가려지거나 화면을
벗어나면 현재 추적을 중단한다. 불확실성을 개체 부재 또는 정지로 표현하지 않는다.

## 관측 버퍼와 반응 지연의 구분

짧은 이력 버퍼는 AI가 생각하는 동안 지나간 장면을 나중에 읽게 해준다. 이미 지나간
회피 시점을 되돌리지는 못한다. 빠른 반응에는 최신 관측에 접근하는 플레이어 실행 루프가
별도로 필요하다. LLM, 로컬 반응 정책, 제한된 블록의 책임을 명시한다.

| 자료 | 실험 시작 후보 | 읽기 인터페이스의 역할 |
| --- | --- | --- |
| 최신 상태 | 적체 없이 최신 값 우선 | 현재 상태 즉시 조회 |
| 수치·벡터 이력 | 10Hz, 최근30~60초 | 순번 이후 또는 시간 구간 조회 |
| 영상 | 캡처 최적화 후5~15fps부터 측정, 최근10~30초 | 필요한 프레임·짧은 구간 선택 |
| 소리 이벤트 | 순번과 시각을 가진 제한된 버퍼 | 미수신 이벤트 조회, 누락 표시 |
| 장기 경험 | 선택한 관측·판단·행동·결과 | Obsidian·git으로 회고와 이전 |

메모리/임시 저장소의 순환 버퍼와 영구 경험 저장소를 분리한다. 영상·구조화 자료의 실제
시각과 프레임 연결을 유지한다. 현재 상태의 유효기간과 과거 자료의 보존기간은 다르다.
가림 이전의 과거 관측을 회고하는 것은 가능하지만 현재 좌표로 사용해서는 안 된다.
공개 버퍼에는 수집 당시 허용된 정보만 넣는다. 원본 내부 모델 기록을 플레이어에게 열지 않는다.

현 PNG 경로를10회/초로 단순 확대하면85ms×10=850ms/초의 비용이라는 추산이 된다.
이는 고속 촬영 실측이 아니다. 압축 영상·메모리 버퍼·설치 버전에서 가능한 캡처 경로를
검토해야 하며, PNG 파일을 대량 생성하는 것만으로 해결하지 않는다.

## 블록은 플레이어가 작성한 제한된 절차

게임기는 범용 블록 실행기와 관측/입력 제한을 제공한다. 무엇을 언제 클릭할지,
어떤 조건을 중요하게 볼지, 언제 블록을 활성화할지는 플레이어가 정한다.
게임 규칙을 미리 아는 ‘특정 환상체 자동 관리’ 블록은 기본 제공하지 않는다.
사용자가 든 주기적 클릭은 인터페이스 예시이며 실제 게임 규칙으로 확정하지 않는다.

이 방식은 플레이어가 배운 행동을 명시적인 절차로 저장하는 수단이다. 모델이 바뀌어도
블록 사양과 근거 경험을 함께 이전할 수 있다. 절차의 존재만으로 새 모델의 숙련이나
성공을 보장하지 않으며, 활성화 전 현재 관측과 호환성을 다시 확인한다.

### 합의한 단순 블록 방향

| 종류 | 허용 역할 | 제외할 역할 |
| --- | --- | --- |
| 주기 | 지정 간격마다 신호 발생 | 내부에 조건·클릭·재시도 절차까지 내장 |
| 조건 | 최신 허용 관측값 하나를 기준값과 단순 비교 | 내부 상태 조회, 자동 위험 해석, 임의 코드 |
| 키 입력 | 지정 키 하나를 제한된 시간 동안 누름 | 복잡한 조작 시퀀스, 게임 함수 직접 호출 |
| 클릭 | 지정 대상에 클릭1회; 기존 논의의 단순 입력 | 숨은 대상 명령, 내부 반복·자동 탐색 |
| 횟수 제한 | 신호를 정해진 횟수만 통과시킴 | 자기 초기화로 제한 우회 |

카메라 이동은 별도 복합 블록 대신 방향키 입력 등 실제 조작으로 구성한다.
가시성·조작 가능성·관측 만료 검사와 중단·입력 해제는 실행기의 필수 규칙이다.
플레이어가 검사 블록을 넣지 않았다고 숨은 대상을 클릭할 수 없어야 하며,
필수 장치 검사는 사용 가능한 블록 개수에서 차감하지 않는다.

예: ‘플레이어가 화면에서 지정한 대상 → 5초마다 → 지금도 같은 대상을 클릭할 수
있는지 검사 → 클릭1회 → 최대3회 또는20초 뒤 종료’. 이 수치는 게임에 적합한 주기의
주장이 아니다. 실행 결과는 입력 전달과 실제 게임 효과를 구분해 기록한다.

### 화면과 조작 가능성의 한계

- 고정 화면 좌표와 대상을 따라가는 클릭을 구분한다. 고정 좌표는 카메라·UI 배치가 바뀌면 무효화한다.
- 대상을 따라가는 블록도 최신 화면에서 연속적으로 확인된 대상에만 결합한다. 현재 익명 벡터 ID만으로 클릭 가능성을 보장하지 않는다.
- 월드 개체의 ‘보임’과 UI의 ‘클릭 가능함’은 별도다. 모달 창, 튜토리얼 입력 제한, 클릭 가로채기, 비활성 UI를 함께 검사한다. 확인할 수 없으면 실행을 보류한다.
- 가려짐·화면 이탈·관측 만료·씬 전환·추적 단절이면 대상 클릭을 보류한다. 마지막 좌표, 숨은 모델 ID, 내부 경로로 이어서 클릭하지 않는다.
- 대상의 재등장은 기존 대상의 확인으로 자동 간주하지 않는다. 초기안에서는 플레이어가 새 관측으로 다시 결합해야 한다.
- 주기 클릭 블록이 스스로 화면을 돌려 대상을 찾지 않는다. 카메라 이동은 플레이어가 별도로 설정한 제한된 절차여야 한다.
- 가림 여부의 검증과 입력 적용 사이에도 상태가 바뀔 수 있다. 가능한 한 입력 적용 프레임에서 재검사하고, 확인 불가능한 렌더 효과에서는 보류한다. 무오류를 가정하지 않는다.

### 사용자가 조절하는 총 블록 한도

핵심 밸런스 설정은 총 블록 한도 하나로 단순화한다. 실행 구성에 배치한 블록 하나를1개로
계산하고, 연결한 절차 전체의 합을 제한한다. 저장만 한 과거 설계도와 현재 배치 구성은
구분한다. 활성 절차 수만 세거나 복합 기능을 한 블록으로 포장해서 한도를 우회하지 않는다.

사용자는 플레이를 보며 필요할 때 한도를 늘린다. 플레이어는 부족함을 설명할 수 있지만
자기 한도를 변경하지 않는다. 초기 개수는 아직 정하지 않았다. 앞서 제안했던 활성 절차3개,
절차당8개 노드는 채택하지 않는다. 단순 기능의 조합과 사용자 조정으로 시행착오를 수집한다.

한도와 별개인 실행 제약 및 추가 검토 사항은 다음과 같다. 아래 수치를 새 밸런스 규칙으로
확정한 것은 아니다.

- 임의 복합 블록·하위 절차로 개수를 숨기지 않는다. 초기에는 임의 순환 연결을 허용하지 않고 주기 블록으로 반복한다.
- 임의 코드·네트워크·파일·프로세스 접근 없음. 무한 반복·재귀·절차의 자기 복제·전체 개체 순회 없음.
- 초기 전체 입력 예산은 초당2회 같은 낮은 값부터 측정. 이 값이 게임에 충분하다고 가정하지 않는다.
- 입력은 하나의 가상 포인터·키보드에서 조정한다. 여러 절차가 동시에 다른 위치를 클릭하지 못한다.
- 활성화 유효기간 최대60초 같은 유한 임대, 반복 횟수·개별 키 유지시간도 제한. 갱신은 플레이어의 명시적 결정으로 기록한다.
- 주기는 우선 실제 경과시간으로 정의하고, 지연된 타이머는 한꺼번에 따라잡지 않는다. 게임 일시정지·배속 때의 정책은 별도 결정하며 숨은 시간 상태를 사용하지 않는다.
- 우선순위는 운영자 중단, 플레이어의 직접 입력, 사전 설정한 블록 순서로 검토한다. 기존 동작 취소 시 눌린 키·버튼을 해제한다.
- 큐 대기 중에도 관측 만료를 검사한다. 입력 충돌·실패로 미뤄진 명령을 나중에 무조건 재생하지 않는다.
- 장치가 모든 블록을 중지하는 것과 게임 시간을 정지시키는 것은 별개다. 게임의 정지 제한은 우회하지 않는다.

블록을 한 번 만들었다고 LLM이 완전히 빠져도 되는 것은 아니다. 조건이 달라지거나
경험하지 않은 상황이 생기면 보류 결과와 관측을 받고 플레이어가 다시 판단해야 한다.
다만 매 클릭마다 LLM 승인 또는 자연어 설명을 요구하면 지연을 다시 만들므로,
활성화 때 의도·근거를 기록하고 각 실행은 간결한 사건 로그로 남긴다.

## 관찰과 경험 기록

관찰 화면에 배치 블록 수/총 한도, 활성 절차, 결합 대상, 다음 실행 예정, 남은 횟수·시간,
최근 실행, 보류·취소 이유를 표시하는 방안을 검토한다. 관찰 창에서 게임 입력을
직접 보내지 않는 기존 원칙을 유지하며, 운영자 중단은 별도 제어 경로를 따른다.

기록은 블록 버전·작성 모델·근거 관측/경험·활성화 의도, 매 실행의 관측 순번과 시각,
조건 결과·입력 전달 응답·사후 결과, 실패와 수정 이력을 연결한다. 사람이 개입하면
별도 사건으로 남긴다. 자동 로그를 모델의 내적 사고나 직접 플레이한 경험으로 꾸미지 않는다.
블록의 효과는 사람 반응과 동일한 조건의 플레이가 아니라 제한된 자동화 조건으로 표시한다.

사용자가 한도를 바꾸면 시각·이전 한도·새 한도·변경 주체를 기록하고, 이유는 제공된 경우
함께 남긴다. 변경을 플레이어에게 알린다. 변경 전후의 경험에는 당시 한도를 연결하여,
도구가 늘어난 효과와 플레이어가 배워서 개선된 효과를 구분할 수 있게 한다.
‘충분한 시행착오’는 사용자의 관찰에 따른 판단이며 시스템이 임의로 점수화해 자동 해금하지 않는다.

## 다음 검토 순서

1. 관측 수집·읽기·입력 완료 대기를 분리하고 최신 게시가 오래된 자료에 밀리지 않게 설계한다.
2. 캡처와 가시성 판정 비용, 입력 보호 검사 비용을 구분해 측정한다. 이후 짧은 버퍼를 추가한다.
3. 표시 어댑터를 환상체·시련·투사체 계열로 나누어 확인한다. 대규모 개체 수에서 비용과 누락을 측정한다.
4. 고정 기능 블록과 사용자 조절 총 한도를 설계한다. 입력량·유효기간 등 실행 제약은 반응성에 미치는 영향을 검토한다.
5. 가림, 화면 이탈, 카메라 이동, 씬 전환, 모달 UI, 관측 만료, 충돌, 운영자 중단에서 오입력이 없는지 검증한다.
6. 관측 시점→조건 판정→입력 적용까지의 지연을 중앙값·95백분위·최악값으로 보고한다. 게임 FPS 영향과 후반 부하를 함께 측정한다.

원본 세이브 보호와 가상 입력 분리는 유지한다. 블록 실행 자체에는 유료 모델 호출이
필요하지 않다. 단순 비교·타이머·입력 조정으로 구현 가능하나 실제 성능과 게임 밸런스는 검증 대상이다.

## PNG 대안 추가 검토

2026-10-18 사용자가 PNG보다 효율적인 형식과 전달 방식을 질문했다. 구현은 미실시다.

- 정지 이미지: JPEG를 첫 비교 후보로 둔다. 복사본의 UnityEngine.ImageConversionModule.xml에 EncodeToJPG가 명시되어 있다. 품질80~90부터 작은 글씨·공격 효과 보존과 크기/지연을 비교하되 확정 품질은 아니다. WebP는 별도 인코더·읽기 경로를 검토해야 하며 작은 파일이 반드시 빠른 인코딩을 의미하지 않는다.
- 로컬 전달: 최신 프레임을 메모리에 두고 공유 메모리 또는 로컬 통신으로 전달하는 경로를 검토한다. 파일 저장/재읽기를 줄일 수 있지만 GPU에서 CPU로 복사하는 비용까지 자동으로 제거하지는 않는다. GPU 공유 텍스처는 별도의 캡처/동기화 구현이 필요하다.
- 연속 이력: GPU 하드웨어 인코딩 H.264와 짧은 순환 버퍼를 후보로 둔다. 로컬 확인 결과 GPU는 RTX4060이다. NVENC/FFmpeg의 실제 구동과 저지연 설정은 아직 검증하지 않았다. AI에게 영상 전체를 계속 보내지 않고 필요 시 프레임/구간을 추출한다.
- 최종 합성된 게임 화면만 캡처한다. 특정 카메라의 렌더 타깃만 읽다가 UI·보스 가림 효과를 빠뜨려서는 안 된다. Windows의 게임 창 캡처도 대안이지만 최소화·가림·해상도 변경·커서와 프레임 시각 일치는 검증해야 한다.
- 현재 PNG 캡처 약85ms에는 ReadPixels·인코딩·주변 처리 비용이 섞여 있다. 단계별 측정 없이 JPEG로 바꾸면 이 비용이 모두 사라진다고 주장하지 않는다.
- 우선 후보는 최신 프레임의 메모리 보관 + 요청 시 JPEG, 연속 기록용 H.264, 무손실 검증용 PNG의 용도별 분리다. 형식 변경만으로 AI 추론 지연이나 비용이 같은 비율로 줄어들지는 않는다. 실제 모델 연결에서 지원하는 이미지/영상 입력을 확인한다.

참고: [Unity 2017.4 JPEG API](https://docs.unity3d.com/2017.4/Documentation/ScriptReference/ImageConversion.EncodeToJPG.html), [Windows 화면 캡처](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture), [NVIDIA FFmpeg 하드웨어 인코딩](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/ffmpeg-with-nvidia-gpu/index.html).
